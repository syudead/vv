# Research: requirements.md と別担当者承認必須ルールの廃止

## R-601: 組み込みチェックリストだけを廃止する

**Decision**: Spec Kit が暗黙に管理する `checklists/requirements.md` を廃止し、利用者が
`speckit-checklist` で明示的に作る目的別チェックリストは残す。

**Rationale**: Issue #53 が問題にしているのは、仕様生成時の自己確認結果が要求成果物として
永続化され、後続工程のゲートにも使われることだからである。明示的に依頼された UX、security、
test などのチェックリストは別の用途と所有者を持つ。

**Alternatives considered**:

- `checklists/` 自体を廃止する: 利用者が明示的に必要とするレビュー補助まで失うため不採用。
- 組み込みファイルを別名にする: 正本が複数ある問題を名前だけ変えて残すため不採用。

## R-602: 仕様品質確認は一時検証として実行する

**Decision**: `speckit-specify` は従来の品質観点をその場で検査し、不備を `spec.md` に反映する。
検査結果専用のファイルは作らない。`speckit-clarify` も更新後の spec 自体だけを検証する。

**Rationale**: 品質観点は有用だが、その結果を永続化すると要求の正本と並ぶ第二の状態になる。
成果は改善された `spec.md` で十分に観測できる。

**Alternatives considered**:

- PR コメントへ自己検査結果を必須記録する: 保存先を変えただけで不要な必須状態が残るため不採用。
- 品質検査そのものを削除する: 曖昧さやテンプレート残骸を早期に直す価値を失うため不採用。

## R-603: 別担当者の承認を SDD ゲートにしない

**Decision**: 仕様作成者とは別の人、agent、セッションによる approve を Plan や実装の開始条件に
しない。通常の PR レビューと人によるマージ判断は任意の開発運用として残す。

**Rationale**: 必須承認は Issue #53 の利用者要求に反し、作業を進めるためだけの追加セッションを
要求する。仕様品質の内容規則と GitHub の一般的なレビューは、専用ゲートなしでも利用できる。

**Alternatives considered**:

- bot の COMMENTED 判定を承認として扱う: bot 固有の状態に工程を依存させるため不採用。
- approve は必須だが reviewer の独立性だけを外す: 自己承認用の形式的操作が残るため不採用。

## R-604: 現行ファイルだけを移行し、履歴は書き換えない

**Decision**: 現在のスキル、テンプレート、文書、feature artifacts を更新・削除する。
Git 履歴、closed PR、Issue の変更履歴は対象外とする。

**Rationale**: 現行の利用者が参照する入口から旧運用を消せば再発を防げる。履歴改変は
監査可能性を損ない、目的に対して過剰である。

**Alternatives considered**:

- Git 履歴を書き換える: 破壊的で、共同作業の参照を壊すため不採用。
- 既存ファイルを deprecated として残す: 検索結果に旧手順が残り、再利用されるため不採用。

## R-605: 残存検査を受け入れ証拠にする

**Decision**: ファイル列挙と `rg` により、対象ファイル、旧ライフサイクル参照、必須承認文言、
削除済み手順へのリンクが 0 件であることを確認する。最後に `git diff --check` を実行する。

**Rationale**: 今回の成果は「存在しないこと」が中心であり、リポジトリ全体の検索がもっとも直接的で
再現可能な検証になる。

**Alternatives considered**:

- 手動レビューだけで確認する: 見落としを定量的に示せないため不採用。
- 専用テストプログラムを追加する: 一度きりの文書移行に新しい保守対象を増やすため不採用。
