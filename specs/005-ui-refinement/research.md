# Phase 0 Research: 原案デザインに合わせた UI の再構築

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Date**: 2026-09-15

本機能は「機能を変えずに構図を原案に一致させる」ものなので、未確定なのは**どう作れば
既存の振る舞いを壊さずに済むか**と**裏側の無い要素をどう扱うか**に集中している。
サーバー側の判断は無い。

決定は R-501 から R-511 まで。各項目は Decision / Rationale / Alternatives の 3 点で書く。

---

## R-501: 3 領域のレイアウトで、スクロールの持ち主を誰にするか

**Decision**: **文書（ウィンドウ）がスクロールし続ける**。サイドバー（C1）とヘッダー（C5）を
`position: fixed` で画面に固定し、コンテンツ側は `padding-left` / `padding-top` で
その分だけ避ける。サイドバーの中身は自分の高さを超えたら独立してスクロールする
（`overflow-y: auto`）。`display: grid` の器を作って**内側にスクロール容器を置く案は
採らない**。

**Rationale**: 004 が積んだ 3 つの仕掛けは、すべて「文書がスクロールする」ことを前提に
している。

| 仕掛け | 前提 | 置き場所 |
| --- | --- | --- |
| 一覧の位置の復元 | `window.scrollY` / `window.scrollTo` | `pages/LibraryPage.tsx`、`api/listSnapshot.ts` |
| 密度変更後の位置合わせ | `window.scrollY` と要素の `getBoundingClientRect()` | `pages/LibraryPage.tsx` |
| 無限スクロール | `IntersectionObserver`（`root` 未指定 = ビューポート） | `pages/LibraryPage.tsx` |

スクロール容器を内側の `div` へ移すと、3 つとも書き換えになる（`element.scrollTop`、
`observer` の `root` 指定、復元値の意味の変更、`history.scrollRestoration` の扱い）。
本機能の主目的は構図の再現であり、FR-018／SC-009 は 004 の受け入れ基準が引き続き通る
ことを求めている。**触らないことが、いちばん強い担保になる。**

`position: fixed` でも FR-002（コンテンツのスクロールで移動しない）は満たせる。
ビューポートに対して固定されるので、文書がどれだけ流れても動かない。

**Alternatives considered**:

- **`display: grid` + コンテンツ側 `overflow-y: auto`**: 構図としては素直で、サイドバーと
  コンテンツのスクロールがきれいに分かれる。しかし上の 3 つを同時に書き換えることになり、
  差分が「見た目の変更」から「一覧の中核の作り直し」へ広がる。持ち主を移すのは、
  仮想スクロールのように内側の容器を必要とする変更が来たときでよい。
- **`position: sticky`**: 004 の帯（`Toolbar`）が使っている手である。サイドバーのように
  **画面の高さいっぱいに居続ける**要素には向かない（`sticky` は親の中でしか粘らないので、
  コンテンツより背の低いサイドバーは下端で置いていかれる）。
- **ヘッダーだけ `sticky`、サイドバーだけ `fixed`**: 2 つの規則を並べる理由が無い。
  どちらも「スクロールで動かない」という同じ要求である。

## R-502: 640px の境界をどう表現し、ロゴをどう移すか

**Decision**: 境界は **Tailwind の `sm:`**（`@media (width >= 40rem)` = 640px）をそのまま
使う。独自のブレークポイントを定義しない。ロゴ（C2）は**サイドバーとヘッダーの両方に
置き**、640px 以上ではヘッダー側を `hidden`、640px 未満ではサイドバーごと `hidden` にする。
JavaScript で幅を監視しない。

**Rationale**: spec の受け入れは「幅 640 でサイドバーが表示される（640 が境界）」であり、
`sm:` の `min-width` の向きと一致する。既存の画面（`VideoPage` の情報欄、`Toolbar` の
折り返し）もすでに `sm:` を使っているので、境界が 1 つで済む。

ロゴを 2 か所に置くのは、FR-003 が「ロゴはどの幅でも画面上に存在すること」と
「640px 未満ではヘッダーへ移すこと」を同時に求めているためである。`display: none` は
**支援技術からも消える**ので、読み上げで製品名が 2 回読まれることはない。`hidden` 属性や
`visibility` ではなく `display` で消すことが要点である（[contracts/layout.md](./contracts/layout.md) 3.）。

**Alternatives considered**:

- **`matchMedia` で監視して 1 か所に描く**: 幅の監視、初回描画時のちらつき（サーバー描画は
  無いので実害は小さいが、最初の 1 フレームは必ず既定値で出る）、テストのための
  `matchMedia` の擬似実装を抱え込む。CSS だけで済む分岐に JavaScript を持ち込む理由が無い。
- **CSS の `order` で 1 つのロゴを移動させる**: サイドバーとヘッダーは親が別（片方は
  `fixed` の縦の帯、片方は `fixed` の横の帯）なので、`order` では移せない。
- **`container` クエリ**: 器の幅ではなく**画面の幅**が条件である（サイドバーの有無そのものが
  変わる）。器を基準にすると、サイドバーを消した結果コンテンツが広がり、また出す、という
  振動が起こりうる。

## R-503: 表示のみの要素をどうマークアップするか

**Decision**: **対話要素にしない。** `<button>` にも `<a>` にもせず、`<span>` / `<li>` の
まま描く。`disabled` も `aria-disabled` も付けない。読み上げ向けには、ラベルの直後に
`<span class="sr-only">（未実装）</span>` を添える。視覚的には `--color-inert`（機能する
要素より淡い）で描き、件数を出さない（FR-005）。

**Rationale**: `disabled` と `aria-disabled` は「**いまは**使えない」という意味を持つ。
利用者は条件を探し、満たせば使えると考える。本機能の表示のみの要素は、裏側の機能
そのものが存在しないので、条件は永遠に揃わない — その印は誤りである。

対話要素にしないことには、検査しやすいという利点もある。「押しても何も起きない」
（FR-005）は、`onClick` が無いことではなく**押せる要素として存在しないこと**として
確かめられる。`layout/placeholders.test.tsx` は、サイドバーとヘッダーを描いて
`getAllByRole("button")` / `("link")` に表示のみのラベルが 1 つも現れないことと、
tab 順（`tabIndex >= 0` の要素）に現れないことを確かめる。

FR-006（支援技術に対しても利用できないことが伝わる）は補足語で満たす。「お気に入り」
とだけ読まれると、ただの見出しなのか到達できなかったリンクなのか分からない。
「お気に入り（未実装）」なら、探すのをやめられる。

tab 順に残らないので、SC-005（一覧 → 再生 → 一覧をキーボードだけで往復）の経路が
15 個の空振りで伸びない、という副次的な利得もある。

**Alternatives considered**:

- **`<button disabled>`**: 上記のとおり意味が違う。加えて、無効なボタンは多くのブラウザで
  フォーカスを受けず、読み上げでも読み飛ばされる設定があるため、FR-006 を満たせるかが
  利用者の環境に依存する。
- **`<button aria-disabled="true" tabIndex={-1}>`**: 「いまは使えない」の誤りが残るうえ、
  押せる見た目のまま押せないという最も紛らわしい状態になる。
- **`aria-hidden="true"` で支援技術から隠す**: 視覚利用者だけが原案の構図を見て、読み上げ
  利用者には存在しないことになる。FR-006 に正面から反する。
- **描画しない**: SC-001（原案に写っている要素が同じ領域に同じ順序で存在する）を満たせない。
  spec 冒頭が「機能の有無で要素を省くと構図が変わる」と明示している。

## R-504: アクセントカラーのシアン化と、対比の担保

**Decision**: `--color-accent` を `#63a9f2`（青）から **`#5fd4e4`（シアン）**へ替える。
`--color-accent-ink`（`#07131f`）は変えない。選択中の項目の地として
`--color-accent-surface: #12262b` を足す。新しい組はすべて
`web/src/theme/tokens.test.ts` の対比表に足す。

**Rationale**: 既存の対比表は `accent` を 4 か所（`surface` / `surface-raised` /
`surface-sunken` / `accent-ink`）で使っている。色を替えるだけでその 4 つが動くので、
値の選定と検査を切り離せない。`#5fd4e4` は原案のシアンに近く、かつ暗い地の上で余裕を
持って基準を超える。

| 前景 | 背景 | 必要 | 計算値 |
| --- | --- | --- | --- |
| `accent` | `surface` | 4.5 | 10.82 |
| `accent` | `surface-raised` | 4.5 | 9.68 |
| `accent` | `surface-sunken` | 3.0 | 11.41 |
| `accent-ink` | `accent` | 4.5 | 10.72 |
| `accent` | `accent-surface` | 4.5 | 8.99 |
| `body` | `accent-surface` | 4.5 | 13.24 |

（WCAG 2.1 の相対輝度で計算した値。**単体テストが同じ計算を CSS の値に対して行う**ので、
この表は読み手のための写しである。）

表示のみの要素の色 `--color-inert: #6b7482` は、`surface` で 4.00、`surface-raised` で
3.58 と基準を下回る。**これは FR-011 が明示的に対象外としているもので、意図的である** —
「淡く見える」ことが要求だからである。ただし「機能する要素より確実に淡い」ことは
検査する（`inert` の相対輝度 < `muted` の相対輝度）。値を淡くしすぎて読めなくなる方向と、
濃くしすぎて `muted` と見分けが付かなくなる方向の、後者だけが機械で防げる。

**Alternatives considered**:

- **Tailwind の `cyan-400` をそのまま使う**: `web/src/**` に既定パレット名を書くことは
  004 の `noRawColors.test.ts` が禁じている（FR-001 の実体）。役割名のトークンにする。
- **`accent-ink` も替える**: 替える理由が無い（`#07131f` は新しい accent の上で 10.72）。
  替えれば検査対象が増えるだけである。
- **表示のみの要素を `muted` + `opacity`**: 重なりによって実効値が変わり、どの組を検査すれば
  よいかが決まらない。不透明なトークンにすれば、明暗の順序を CSS だけで確かめられる。
- **選択中を「地は変えず文字と左の棒だけ accent」にする**: 原案は選択行に薄いシアンの
  地を敷いている。SC-001 の判定は色を見ないが、地が無いと選択の強さが原案と変わる。
  トークン 1 つで済むので足す。

## R-505: 再生画面の 2 分割を、どの幅でどう畳むか

**Decision**: 左に映像、右に情報パネル（C14）を置き、**一覧と同じ 640px の境界**で
縦に畳む（`sm:` 未満はパネルが映像の下）。パネルの幅は固定せず、`sm:` 以上で
`minmax(18rem, 24rem)` の範囲に置く。再生画面には `AppShell` を被せない（FR-015）。

**Rationale**: 境界を 2 つ持たない。利用者から見て「サイドバーが消える幅」と「パネルが
下へ回る幅」が別だと、狭くしていく途中で 2 回構図が変わる。

パネルの幅を固定しないのは、映像の側を優先するためである。映像は比率を保ったまま
残りに収まる必要があり（004 の FR-012 由来の振る舞い）、パネルが固定幅だと幅 640〜800px で
映像が極端に細くなる。下限 `18rem` は MetaList のラベルと値が 1 行に収まる幅、上限
`24rem` は原案のパネル幅の見当である。

`AppShell` を被せないのは spec が明記している（FR-015: サイドバー・ヘッダー・見出し文字を
表示しない）。`App.tsx` で経路ごとに器を変えるのがいちばん素直で、再生画面が骨格の
存在を知らずに済む。

**Alternatives considered**:

- **独自の境界（例 768px / 900px）を作る**: 上のとおり、構図の変わる点を増やす。
- **`AppShell` を被せたうえで、再生画面のときだけサイドバーとヘッダーを消す**: 骨格が
  「いまどの画面か」を知ることになる。経路の分岐は `App.tsx` の 1 か所で足りる。
- **パネルを固定幅（例 320px）にする**: 幅 640〜800px で映像が細くなりすぎる。

## R-506: 密度をスライダーにしたとき、保存の形をどうするか

**Decision**: `localStorage` の鍵 `vv.view.v1` と値の形（`{"density":"standard","sort":"addedDesc"}`）を
**変えない**。スライダーは `<input type="range" min="0" max="2" step="1">` とし、位置と
`Density` の対応を 1 つの配列（`["dense","standard","relaxed"]`）だけで読み替える。
`aria-valuetext` に段階の名前（「細かい」「標準」「ゆったり」）を入れる。

**Rationale**: FR-013 は「利用者が実際に行える操作の種類と数を変えない」ことと
「密度変更は従来どおり行えること」を求めている。保存の形を変えると、いま
`standard` 以外を選んでいる利用者の設定が読めなくなり、**従来どおりではなくなる**。
004 の `readViewPreferences` は壊れた値を既定値へ落とすので画面は出るが、それは
「設定が消えた」ということである。

読み替えを配列 1 つに閉じるのは、往復（`Density → index → Density`）が恒等であることを
1 つの検査で確かめられるようにするためである。

`aria-valuetext` が要るのは、range が既定で数値（「1」）を読むからである。段階の名前は
画面に出ている文言と同じにする。

**Alternatives considered**:

- **保存値を数値に替え、読み出し時に古い文字列を移行する**: 移行の処理と、その処理の
  検査と、「移行のあとに古い版を開いたら」という場合が増える。得るものは無い。
- **`<select>` のまま見た目だけスライダーに見せる**: spec は C12 を DensitySlider と
  定めている。見た目だけ似せると、キーボードの操作（矢印キーで段階を動かす）が
  スライダーの期待と食い違う。
- **段階を増やす（5 段階など）**: FR-013 に反する（選べるものが増える）。

## R-507: 情報パネルの中身（C16 MetaList）をどう並べるか

**Decision**: いまの 6 項目（長さ・解像度・形式・映像・音声・大きさ）と、取れていない値の
言い分け（「確認中」「読み取れませんでした」「なし」）を**そのまま保つ**。変えるのは
体裁だけで、値から `font-mono` を外し、ラベルは `--color-muted`、値は `--color-body`、
1 項目 1 行として行間に区切り線を置く。`<dl>` / `<dt>` / `<dd>` の構造は変えない。

**Rationale**: FR-016 は「等幅フォントの羅列であってはならず、項目名と値が読み分け
られる体裁で示すこと」だけを求めている。値そのものは spec の Assumptions が
「内容は変えず、表示形式だけ変更する」と決めている。

`<dl>` を保つのは、読み上げにラベルと値の対が伝わる構造がすでにあるからである。
見た目のために `<div>` の並びへ崩すと、004 が得ていたものを失う。

`font-mono` を外して困るのは解像度（`1920 × 1080`）の桁揃えだが、項目が縦に 1 つずつ
並ぶ以上、揃える相手がいない。

**Alternatives considered**:

- **表（`<table>`）にする**: 1 列 2 行の対が 6 つ並ぶだけで、行と列の関係が無い。
- **値だけ等幅を残す**: FR-016 が「等幅フォントの羅列」を名指しで禁じている。
- **項目を減らす / 増やす**: spec のスコープ外（減らすと機能が減る、増やすとサーバーが
  持っていない）。

## R-508: 見出し（`h1`）を誰が持つか

**Decision**: `h1` は**ロゴ（C2）**が持つ。一覧の見出し文字（いまの `<h1>vv</h1>`）は
消す。件数は原案どおりツールバーの右へ移し、004 の「変化を知らせる領域」
（`role="status"` / `aria-live="polite"`）はそのまま連れて行く。サイドバーの
NavItem「すべての動画」の右端にも実数を出す（FR-005 / spec 5.）。

**Rationale**: 原案の一覧には見出し文字が無い。ロゴが製品名を持ち、タブが現在の区分を
示す。`h1` を 2 つ置くか、どちらも置かないかの二択になるので、**どの幅でも画面に存在する
と決めた要素**（FR-003 のロゴ）に持たせるのが素直である。

件数の読み上げは 004 の FR-008／FR-021 に由来し、FR-018 が引き続き満たすことを求めて
いる。置き場所が変わるだけで、文言（「N 本」「「語」に一致 N 本」「読み込み中…」）も
`aria-live` も変えない。

NavItem とツールバーで件数が 2 か所に出るのは原案どおりである。同じ値なので食い違わない
（どちらも一覧の `total` を読む）。

**Alternatives considered**:

- **一覧に見えない見出し（`sr-only` の `h1`）を残す**: 見出しが 2 つになる。ロゴが読まれる
  以上、追加の情報が無い。
- **件数をサイドバーだけに出す**: 原案はツールバーの右にも出しており、SC-001 の判定
  （原案の要素が同じ領域に存在する）に引っかかる。
- **件数の `aria-live` を落とす**: FR-018 に反する（004 の受け入れ基準）。

## R-509: キーボードの到達順をどう決めるか

**Decision**: DOM の順序をそのまま到達順にする。`tabIndex` で順序を操作しない。
順序は **サイドバー（ロゴ → 「すべての動画」）→ ヘッダー（「動画」タブ）→ ツールバー
（探す → 並べ替える → 密度 → 取り込む）→ 一覧の項目** とする。表示のみの要素は
[R-503](#r-503-表示のみの要素をどうマークアップするか) により到達順に現れない。

**Rationale**: 004 の `screen-states.md` 3. が定めた到達順（帯 → 一覧）は、その前に骨格の
2 つが挟まるだけで保たれる。順序を DOM に一致させておけば、要素を足したときに
到達順が壊れる余地が無い。

ロゴを到達可能にするのは、一覧へのリンク（`/`）を兼ねるためである。原案でもロゴは
左上の起点であり、検索や絞り込みのあとに一覧の素の状態へ戻る道になる。**これは操作を
増やしていない** — 既存の一覧 URL へ行くリンクで、`Tab` の「ライブラリ」項目と同じ
行き先である。

SC-005（マウス 0 回で一覧 → 再生 → 一覧）は、再生画面側の × ボタン（C15）が最初の
到達先であることで満たす。

**Alternatives considered**:

- **骨格をスキップするリンク（skip link）を足す**: 到達順に入る要素が 4 つ（ロゴ・
  「すべての動画」・「動画」タブ・帯）しかないので、飛び越す価値が無い。要素が増えたら
  そのとき入れる。
- **`tabIndex` で帯を先頭にする**: DOM と到達順がずれると、以後の変更のたびに両方を
  考えることになる。

## R-510: アイコンをどこから持ってくるか

**Decision**: 必要な 10 個程度（映画・時計・ハート・フォルダ・タグ・虫眼鏡・漏斗・歯車・
格子・一覧・×）を **インラインの `<svg>`** として `web/src/layout/icons.tsx` に置く。
外部のアイコン集（`lucide-react` 等）を依存に足さない。

**Rationale**: 技術選定の判断基準は「常駐するものを増やさない」「後から重くできる境界を
先に引く」である。10 個のために数百個を抱える集を入れると、実行時の依存が 1 つ増え、
版上げの対象も 1 つ増える。インラインなら `currentColor` で色がトークンに従い、
`aria-hidden="true"` を付けて読み上げから外す扱いも 1 か所で決まる。

**Alternatives considered**:

- **`lucide-react` などを入れる**: 依存 1 つ（tree-shaking で出力は小さいが、版と
  ライセンスの管理対象は増える）。本機能は「依存を 1 つも増やさない」と宣言できるほど
  必要数が少ない。
- **絵文字で代用する**: 環境ごとに字形が変わり、色がトークンに従わない。
- **スプライト（`<use href="#icon">`）**: 埋め込みの SPA なので参照先の管理が増えるだけで、
  10 個では利得が出ない。

## R-511: 「構図が原案と一致している」ことをどう検証するか

**Decision**: 機械で確かめるのは (a) 対比と明暗の順序、(b) 表示のみの要素が対話要素で
ないこと、(c) 密度の読み替えの往復、(d) 情報パネルの体裁と 6 項目の存在、の 4 つに
限る。**構図そのもの（SC-001）と画面幅による出し分け（SC-003・SC-007）は
[quickstart.md](./quickstart.md) S2〜S6 で人が原案と並べて確かめる。**

**Rationale**: jsdom は CSS を適用しないので、`position: fixed`・メディアクエリ・
`grid-template-columns` のどれも検査できない。ここで擬似的に確かめる仕掛けを作ると、
「テストは通るが画面は壊れている」という最悪の状態を招く。

SC-001 の判定基準は spec が「要素の有無と並び順だけで行い、画素単位の一致は求めない」と
定めている。これは人が原案と並べて見るのに適した基準である。

画像の取得手順は [docs/how-to/ui-change-screenshots.md](../../docs/how-to/ui-change-screenshots.md)
にあり、コンテナ内でも Playwright で撮れる。撮る 6 枚は quickstart S8 に定める。

**Alternatives considered**:

- **視覚回帰テスト（スクリーンショット比較）を入れる**: 依存が増え、環境ごとの字形差で
  誤検知が出る。本機能で入れると、以後すべての UI 変更が基準画像の更新を伴う。
  Playwright は Phase 3 の範囲である（技術選定文書 8.）。
- **jsdom でメディアクエリを擬似する**: 擬似実装が正しいことを誰も確かめられない。
- **何も機械で確かめない**: (a)〜(d) は DOM と CSS のテキストだけで確かめられるので、
  人に回す理由が無い。
