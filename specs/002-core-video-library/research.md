# Phase 0 Research: 絞られたコア機能（動画ライブラリの中核）

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Date**: 2026-09-12

技術の採否は[技術選定文書](../../docs/design-docs/tech-stack-selection.md)で決定済みで
あり、骨組みは [001](../001-initial-setup/plan.md) で通っている。本書は、その上に

## R-101: 移動・改名を越えて同じ動画と判定する鍵（`content_key`）

**Decision**: `content_key` = `sha256(先頭 1MiB ‖ 末尾 1MiB) + ":" + ファイルサイズ`
の 16 進表現。2MiB 以下のファイルは全体を1度だけ読んで同じ式に当てる。ハッシュ関数は
**標準ライブラリの `crypto/sha256`** を使い、新しい依存は足さない。

**Rationale**: 数 TB のライブラリで全体ハッシュは非現実的（技術選定文書 3.2）。
先頭と末尾を取るのは、多くの動画コンテナが先頭にヘッダ、末尾に索引（mp4 の `moov` が
末尾に来る場合を含む）を持ち、内容が違えばどちらかが変わるためである。サイズを鍵に
含めることで、偶然の衝突は実質的に無視できる。

ハッシュ関数について、技術選定文書は BLAKE3 と書いているが、**読む量が1ファイル
あたり最大 2MiB に固定されている**ため、速度差は取り込み時間を律速しない（律速は
`ffprobe` の起動とディスク I/O）。標準ライブラリの SHA-256 は amd64／arm64 で
ハードウェア命令が使われ、依存を増やさずに済む。この差分は技術選定文書へ反映する
（tasks で文書更新として扱う）。

**Alternatives considered**:

- 全体のハッシュ: 数 TB を読み直すことになる。初回取り込みが現実的な時間に収まらない。却下
- `lukechampine.com/blake3`: CGO 不要で高速だが、2MiB では利点が出ない。依存を1つ増やす
  理由がない
- inode + デバイス番号: 同一ファイルシステム内の移動しか追えず、コピーや別ボリュームへの
  移動で破綻する。却下
- パスだけを鍵にする: 改名・移動のたびに別の動画として扱われ、FR-004／FR-025 を満たせない

**実装上の注意**: 読み取りは `io.ReaderAt` で 2 回。ファイルが 1MiB 未満のときは
先頭・末尾が重なるため全体を1回だけ読む。取り込み中に書き込み途中のファイル
（`.part`／`.crdownload`／`.!ut`）は対象外にする（R-110）。

## R-102: メタデータの取得方法（`ffprobe`）

**Decision**: 1ファイルにつき次の1回だけ実行し、標準出力の JSON を解析する。

```text
ffprobe -v error -print_format json -show_format -show_streams -- <path>
```

取り出す値は `format.duration`・`format.format_name`、`streams[]` のうち
`codec_type=video` の先頭から `codec_name`・`width`・`height`、`codec_type=audio` の
先頭から `codec_name`。実行は `exec.CommandContext` に **30 秒**のタイムアウトを与え、
`internal/media` の外へ `os/exec` を漏らさない。

**Rationale**: `-show_format -show_streams` の1回で必要な値がすべて揃う。JSON 出力は
解析が安定しており、ロケールに依存しない。タイムアウトは、壊れたファイルで `ffprobe` が
戻らない場合に取り込み全体を止めないため（FR-008）。

**Alternatives considered**:

- 値ごとに `-show_entries` で複数回実行: プロセス起動が支配的なコストなので遅くなる
- Go のライブラリでコンテナを解析: 対応形式の維持コストを自前で抱える。`ffmpeg` は
  すでに必須依存（001 の起動前確認）なので使わない理由がない

**失敗の扱い**: 終了コードが非 0、JSON が解析できない、`duration` が取れないものは
「取り込めなかったファイル」として記録し、次のファイルへ進む（FR-008）。

## R-103: ブラウザで再生できるかの判定

**Decision**: 拡張子（コンテナ）と `ffprobe` が返したコーデック名の**許可リスト**で
判定し、結果を `playable` と `unplayable_reason` に保存する。

| 判定対象           | 許可する値                                  |
| ------------------ | ------------------------------------------- |
| コンテナ（拡張子） | `.mp4` `.m4v` `.webm`                       |
| 映像コーデック     | `h264` `vp8` `vp9` `av1`                    |
| 音声コーデック     | `aac` `mp3` `opus` `vorbis`、または音声なし |

3つすべてを満たすものだけ `playable = 1`。満たさない場合は、どれが理由かを
`unplayable_reason`（`container` / `video_codec` / `audio_codec`）に残す。

**Rationale**: 判定は取り込み時に1度だけ行い、一覧では列を読むだけにする（SC-007 の
「再生を試みる前に 100% 判別できる」）。許可リストにするのは、未知の値を「再生できる」と
誤って扱うより、「再生できない」と誤る方が利用者の損失が小さいためである。`hevc`（H.265）や
`mkv` は、ブラウザによっては再生できることがあるが、確実ではないので許可しない。

コンテナをコンテナ解析ではなく拡張子で見るのは、`ffprobe` の `format_name` が
`mov,mp4,m4a,3gp,3g2,mj2` のようにまとめて返り、mp4 と mov を区別できないためである。
ブラウザに渡す `Content-Type` も拡張子から決めるので、判定と配信で基準が揃う。

**Alternatives considered**:

- 拒否リスト方式: 未知のコーデックが「再生できる」と表示され、再生して初めて失敗する。
  SC-007 に反する
- ブラウザ側の `canPlayType` で都度判定: 一覧の表示ごとに判定が変わり、サーバー側の
  記録と食い違う。検索・絞り込みにも使えない
- トランスコードして必ず再生できるようにする: スコープ外（spec の Assumptions）

## R-104: サムネイルの生成と保存

**Decision**: `ffmpeg` で1枚の JPEG を生成し、`MDM_DATA_DIR/thumbnails/<先頭2文字>/<content_key>.jpg`
に保存する。抽出位置は「尺の 10%」、ただし下限 1 秒・上限 60 秒。幅 640px に縮小する
（高さは比率維持）。

```text
ffmpeg -nostdin -v error -ss <秒> -i <path> -frames:v 1 -vf scale=640:-2 -q:v 4 -y <出力>
```

**Rationale**: `-ss` を `-i` の前に置くとキーフレーム単位の高速シークになり、長い動画でも
一定時間で終わる。10% 地点にするのは、先頭が黒画面やロゴであることが多いため。
保存先を `content_key` にするとファイルの移動・改名で作り直しが要らず（FR-025）、
2文字のディレクトリに分けるのは1ディレクトリに数万ファイルを置かないためである。

形式は JPEG にする。WebP の方が小さいが、`libwebp` を含む `ffmpeg` ビルドを前提にすると
実行環境の差で失敗しうる。JPEG の mjpeg エンコーダはどのビルドにも含まれる。640px で
おおむね 30〜60KB であり、一覧 60 件でも 2〜4MB に収まる。

**Alternatives considered**:

- 元のフレームをそのままの解像度で保存: 4K だと1枚数 MB になり、一覧の転送量が破綻する
- シークプレビュー用のスプライト: Phase 2 の範囲（技術選定文書 8）。ここでは1枚だけ
- サムネイルを DB に BLOB で持つ: DB を「再構築可能な索引」に留める方針（判断基準2）と、
  `http.ServeContent` による配信のしやすさから、ファイルに置く

**未生成の扱い**: 生成はジョブ（R-106）で非同期に行う。未生成の動画も一覧に並べ、
サムネイルの代わりに枠だけを表示する（FR-010）。

## R-105: 動画の配信（Range 対応）と経路の安全性

**Decision**: `GET /api/videos/{id}/stream` は、DB から取得したパスを開いて
`http.ServeContent` に渡すだけにする。Range の解釈・`206`・`Content-Range`・
`Accept-Ranges`・`416` は標準実装に任せる。開く前に、locationのpathが現在登録済みの
MediaFolderの**内側**にあることを検証する。

**Rationale**: 技術選定文書 3.3 の決定をそのまま実装する。Linux では `io.Copy` が
`sendfile` に落ちるため、大きなファイルでもユーザー空間のコピーが起きない。

パス検証を入れるのは、DB の値をそのまま `os.Open` に渡す実装は、将来 DB へ書き込む
経路が増えたときに任意ファイル読み出しになりうるため。`filepath.Clean` したうえで
各MediaFolder + `string(os.PathSeparator)` を接頭辞として持つことを確認し、満たさない行は
`404` として扱う（存在を漏らさない）。シンボリックリンクは `filepath.EvalSymlinks` 後に
同じ検証を行う。

**テスト**: `httptest` で先頭・途中・末尾・不正範囲・`If-Range` を確認する。標準実装の
再テストではなく、**ハンドラが正しい `io.ReadSeeker` と ModTime を渡していること**の
確認と位置づける（技術選定文書 3.3）。

## R-106: ジョブの実行（取り込み・解析・サムネイル）

**Decision**: `jobs` テーブル + プロセス内のワーカー goroutine **1本**（直列）。
状態は `queued` → `running` → `done` / `failed`。取得は即時トランザクション
（`begin immediate`）で1件を `running` にして専有する。起動時に `running` のまま
残っている行は `queued` に戻す。失敗は `attempts` を増やして `queued` に戻し、
3 回失敗したら `failed` で止める。

**Rationale**: 技術選定文書 3.2／5 の方針（常駐ミドルウェアを足さない、並列度1で
I/O 飽和を避ける）に従う。起動時の巻き戻しがあるため、取り込み中に停止しても
次の起動で再開でき、重複も生まない（spec のエッジケース）。

**Alternatives considered**:

- メモリ上のキューだけで持つ: 停止で失われ、再開できない
- 外部ジョブキュー（Redis 等）: 常駐プロセスが増える。判断基準1に反する
- 並列度を上げる: 初回スキャンで HDD の I/O が飽和し、全体としては遅くなる。
  並列度は設定にせず、必要になった時点で見直す（技術選定文書 6）

**ジョブの種類**: `probe`（メタデータ取得）と `thumbnail`（サムネイル生成）の2種類。
走査そのものはジョブにせず、スキャン処理が同期的にファイルを列挙して `videos` 行を
作り、重い処理だけをジョブに積む。

## R-107: 走査（スキャン）の実装

**Decision**: `filepath.WalkDir` でscan開始時にsnapshotした登録済みMediaFolder以下を再帰的に走る。

- 拡張子の対象: `.mp4` `.m4v` `.webm` `.mkv` `.mov` `.avi` `.wmv` `.flv` `.ts` `.mpg` `.mpeg`
  （再生できない形式も**取り込む**。一覧に出したうえで再生不可と示すため — FR-003）
- 除外: 名前が `.` で始まるファイル・ディレクトリ、`@eaDir`、`#recycle`、
  `lost+found`、書き込み途中の拡張子（`.part` `.crdownload` `.tmp`）
- 実在パスはファイルシステムが返したUnicode表現を保持し、表示名と検索用文字列だけを
  **NFC** へ正規化する。実在パスを書き換えるとLinux等で別の存在しないpathになるため
- 既存行との突き合わせ: パス一致なら `size_bytes` と `mtime` を比較し、変化が
  なければ何もしない（`content_key` の再計算もしない）
- パスに無い行 = 消えたファイル。`content_key` が一致する新しいパスがあれば
  **パスの更新**として扱い（移動・改名）、無ければ行を削除する

**Rationale**: `mtime` と `size` が変わっていなければ内容は変わっていないとみなすのが、
再スキャンを安く保つ唯一の現実的な方法である。これにより 2 回目以降のスキャンは
ディレクトリ走査と DB 比較だけになり、ハッシュも `ffprobe` も走らない。

**移動の判定順序**: 「消えたパス」と「新しいパス」の集合を作り、新しいパス側の
`content_key` を計算して既存行と突き合わせる。新規ファイルのハッシュは
どのみち必要なので、追加コストは無い。

**Alternatives considered**:

- `fsnotify` による常時監視: spec の Assumptions でスコープ外。数万ファイルの監視は
  inotify の上限にも当たる
- すべてのファイルを毎回ハッシュする: 数 TB を毎回読む。却下

## R-108: 取り込みの起点と進捗の見せ方

**Decision**: [007 設定画面](../007-settings-screen/spec.md) により起動時の自動実行は廃止された。
`POST /api/scans`で利用者が明示的に開始する。進行中の状態は
`GET /api/scans/current` が返し、`scans` テーブルに `total` / `completed` / `failed` を
持つ。スキャン中でも一覧・再生の経路は通常どおり応答する（FR-007）。

**Rationale**: 大規模なfilesystem走査の開始時期を利用者が制御できるようにする。スキャンは同時に1本だけ許可し、
実行中の `POST /api/scans` は現在のスキャンを返す（`409` にはしない — 利用者の意図は
「今の状態を進めたい」なので、進行中ならそれを返すのが素直）。

## R-109: 一覧の取得（並び順・ページング・件数）

**Decision**: `GET /api/videos` はカーソル方式（keyset）でページングする。
既定 `limit=60`、上限 200。並び順は `added_at desc, id desc`（追加が新しい順）と
`title asc, id asc`（題名順）の2つ。総件数は同じ応答に `total` として返す。

**Rationale**: 無限スクロールで `offset` を使うと、スキャンで行が増減した瞬間に
取りこぼしと重複が起きる。keyset なら並び順の値と id を境界に使うので安定する。
総件数は FR-012 の要求で、1万件規模の `count(*)` は索引で十分速い。

カーソルは「並び順の値 + id」を base64 で包んだ不透明な文字列とし、クライアントは
中身を解釈しない。

**索引**: `added_at desc, id desc` と `title asc, id asc` に複合索引を1つずつ置く。

## R-110: 検索の経路

**Decision**: 001 の [TD-001](../../docs/exec-plans/tech-debt.md) の方針をそのまま実装する。
検索語の**書記素**が3文字以上なら `videos_fts MATCH`、1〜2文字なら同じ FTS5 表への
`LIKE '%…%'`。検索語は NFC 正規化し、FTS5 の特殊文字（`"` `*` `:` `^` など）は
引用符で包んで無効化する。検索時の並び順は一覧と同じ規則を使う。

**Rationale**: trigram は3文字単位で索引を作るため2文字以下は `MATCH` に一致せず、
日本語では2文字の検索語が多い（001 R-001 の実測）。`LIKE` 経路も trigram 索引で
処理されることは実行計画で確認済みである。

並び順を関連度（bm25）にしないのは、`LIKE` 経路に関連度が無く、2つの経路で並びが
変わると利用者から見て不可解になるため。

## R-111: 再生位置の記録

**Decision**: 記録の鍵は `content_key`（`videos.id` ではない）。クライアントは再生中
**5 秒間隔**と、一時停止・離脱時に `PUT /api/videos/{id}/progress` を送る。離脱時は
`visibilitychange` で `fetch` の `keepalive` を使う。視聴済みの判定はサーバー側で行い、
`position_ms >= duration_ms - 15000` または `position_ms / duration_ms >= 0.95` を満たしたら
`completed = 1` にする。再開位置は、`completed` のとき、または 5 秒未満のときは先頭に戻す。

**Rationale**: `content_key` を鍵にすると、ファイルを消して同じ内容を置き直しても
再生位置が残る。`videos` は「消してもスキャンで再構築できる索引」、
`playback_progress` は「再構築できない利用者データ」であり、技術選定文書の判断基準2
（バックアップ対象の分離）がテーブル単位でそのまま成立する（FR-026）。

5 秒間隔は、書き込み頻度（SQLite への `upsert`）と失う可能性のある視聴時間の釣り合いで
選んだ。複数タブ・複数端末の競合は「最後の書き込みが残る」で割り切る（spec のエッジケース）。

## R-112: サムネイルの配信とキャッシュ

**Decision**: `GET /api/videos/{id}/thumbnail?v=<content_key の先頭 12 文字>` で配信し、
`Cache-Control: public, max-age=31536000, immutable` を付ける。一覧の応答には
`thumbnailUrl` として `v=` 付きの URL を入れる。未生成の場合は `404` を返し、
クライアントは枠だけを描く。

**Rationale**: 内容が変われば `content_key` が変わり URL も変わるので、長期キャッシュが
安全に効く。ETag による再検証にすると、一覧を開くたびに 60 本分の条件付き要求が飛ぶ。

## R-113: フロントエンドの構成（ルータ・データ取得）

**Decision**: ルーティングは `react-router` v7 を**宣言的モードで**導入する
（画面は `/`＝一覧 と `/videos/:id`＝再生の2つ）。データ取得ライブラリ
（TanStack Query 等）は**入れない**。`fetch` と `web/src/api/gen/openapi.ts` の生成型を
使う薄いフックを自前で置く。

**Rationale**: 001 の R-011 は「画面が1つの間は不要」として Phase 1 へ送っていた。
画面が2つになり、戻る操作と URL 共有（再生中の動画を URL で開く）が要るので、
ここで最小のルータを入れる。

データ取得側を入れないのは、この時点の要求が「一覧（無限スクロール）・詳細・進捗送信」の
3種類しかなく、キャッシュ無効化の関係も単純だからである。画面をまたぐキャッシュ整合や
楽観更新が必要になった時点で再検討する（Phase 2）。

**Alternatives considered**:

- ルータを自前で書く: 2 画面なら可能だが、戻る・進む・スクロール位置の復元まで自前に
  なる。無限スクロールの一覧に戻る体験が悪化する
- TanStack Router: 型付きルートは魅力だが、この規模では設定量が利点を上回る

## R-114: 一覧の段階表示（体感速度）

**Decision**: 一覧は無限スクロール（`IntersectionObserver` で次ページ取得）。
サムネイルは `loading="lazy"` と固定アスペクト比（16:9）の枠で描き、読み込み中も
レイアウトが動かないようにする。初回表示は最初の1ページ（60 件）だけを待つ。

**Rationale**: SC-003（1万件でも最初の画面が 2 秒以内）は、全件を読まないことでしか
満たせない。固定枠はレイアウトシフトを防ぎ、体感の安定に効く。

---

## R-115: SQL の書き方（`sqlc` を入れるか）

**Decision**: この段階では入れない。`internal/store` に手書きの SQL と、行を構造体へ
写す薄い関数を置く。

**Rationale**: 001 が Phase 1 送りにした論点。実際に必要な問い合わせは十数本で、うち
検索は2経路の動的な組み立て（R-110）、一覧はカーソル条件の動的な組み立て（R-109）を
伴う。`sqlc` は静的な問い合わせには強いが、この2つは結局手書きになる。生成物と
手書きが混在する方が読みにくい。

**見直しの契機**: 問い合わせが 30 本を超えるか、列の追加でコンパイルエラーにならない
取りこぼしが実際に起きたとき。
