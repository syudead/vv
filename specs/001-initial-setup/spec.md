# Feature Specification: 初期セットアップ（Phase 0 骨組み）

**Feature Branch**: `claude/peaceful-tesla-as1pwp`

**Created**: 2026-09-12

**Status**: Draft

**Input**: User description: "初期セットアップ"

## User Scenarios & Testing *(mandatory)*

本機能の利用者は、このリポジトリで MDM（Media Data Management）システムを実装する
開発者である。現時点でリポジトリには文書しか存在せず、コードを書き始める土台がない。
本仕様は「動くもっとも薄い骨組み」を用意し、以降のフェーズが差分として積める状態を作る
ことを扱う。動画の取り込み・一覧・再生といった利用者向け機能は本仕様の範囲外
（Phase 1 以降）である。

### User Story 1 - clone から起動までを1コマンドで通す (Priority: P1)

リポジトリを取得した開発者が、公開された手順どおりに1つのコマンドを実行するだけで、
アプリケーションがローカルで起動し、ブラウザから「動いている」ことを確認できる。
画面には機能はなく、アプリケーション名と稼働状態が表示されるだけでよい。

**Why this priority**: 起動できない土台の上には何も積めない。ここだけが完成すれば、
以降の作業者は「まず動く状態」から差分を書き始められるため、単独で価値がある。

**Independent Test**: 何も設定されていない環境でリポジトリを取得し、手順書の
コマンドを1つ実行してブラウザで所定のアドレスを開く。稼働状態が表示されれば成功。

**Acceptance Scenarios**:

1. **Given** リポジトリを取得しただけで何も設定していない開発環境、**When** 手順書に
   記載された起動コマンドを1つ実行する、**Then** アプリケーションが起動し、ブラウザ
   から稼働状態を示す画面を開ける
2. **Given** 起動済みのアプリケーション、**When** 稼働確認用のエンドポイントを参照する、
   **Then** 稼働中であることとバージョン情報が機械可読な形式で返る
3. **Given** 初回起動（保存データが存在しない状態）、**When** アプリケーションを起動する、
   **Then** データ保存先が手作業なしに自動で初期化され、起動が完了する
4. **Given** 起動中のアプリケーション、**When** 停止を指示する、**Then** 処理中の作業を
   中断せずに終了し、データを壊した痕跡を残さない

---

### User Story 2 - 壊れた変更が自動で止まる (Priority: P2)

変更を提案した開発者は、人手のレビューを待たずに、書式・静的検査・自動テスト・
設計上の依存方向の違反を自動で検出した結果を受け取れる。違反があれば変更は取り込めない。

**Why this priority**: 骨組みが動いた直後から、境界と品質を機械的に守れる状態にしておく
ほど安い。実装が増えてから後付けすると、既存の違反を一括で直す作業が発生する。

**Independent Test**: 意図的に依存方向の制約に違反する変更、および書式を崩した変更を
作成し、自動検証が失敗することを確認する。制約に沿った変更では成功することも確認する。

**Acceptance Scenarios**:

1. **Given** 制約に沿った変更、**When** 自動検証を実行する、**Then** すべての検査が成功する
2. **Given** ドメイン層が外部入出力に直接依存する変更、**When** 自動検証を実行する、
   **Then** 検証は失敗し、どの依存が禁止されているかが出力から特定できる
3. **Given** 任意の変更提案、**When** 変更を共有リポジトリに提案する、**Then** 同じ検証が
   自動的に実行され、結果が提案に紐づいて見える
4. **Given** 開発者のローカル環境、**When** 検証コマンドを実行する、**Then** 共有環境と
   同じ検査が同じ判定で実行できる

---

### User Story 3 - 採用した基盤の前提を最初に実証する (Priority: P3)

技術選定で「追加のミドルウェアなしに日本語の部分一致検索ができる」ことを前提にして
いるため、実装を積む前にその前提が成り立つことを自動テストで確認できる。

**Why this priority**: 前提が崩れた場合の代替手段への切り替えは、実装が増えるほど高く
つく。骨組みの段階で確認しておけば、影響範囲が保存層の設定のみに収まる。

**Independent Test**: 日本語を含むタイトルを登録し、その一部分だけを検索語として与えて
該当件数が返ることを検証する自動テストを実行する。

**Acceptance Scenarios**:

1. **Given** 日本語のタイトルを含む検証用データ、**When** タイトルの中間部分だけを
   検索語として検索する、**Then** 該当するデータが結果として返る
2. **Given** 前提を満たさない実行環境、**When** 検証テストを実行する、**Then** テストは
   失敗し、代替手段の検討が必要であることが判別できる

---

### Edge Cases

- 外部の動画解析ツールが導入されていない環境で起動した場合、起動時に不足している
  依存と対処方法を示し、原因不明の失敗にしない
- 既定の待ち受けポートが他のプロセスに使われている場合、設定で変更でき、衝突時は
  その旨を明示して終了する
- 保存データが削除された状態で再起動した場合、手作業なしに初期化からやり直せる
- 保存データの形式が現在のアプリケーションより新しい場合、破壊的な変更を加えずに
  起動を中止する
- 外部ネットワークへ接続できない環境でも、取得済みの依存だけで再ビルド・再起動できる
- 自動検証に必要なツールの版が開発者ごとに異なる場合でも、共有環境と同じ判定になる

## Requirements *(mandatory)*

### Functional Requirements

**起動と動作確認**

- **FR-001**: リポジトリは、取得直後の状態から1つのコマンドでアプリケーションを起動
  できなければならない
- **FR-002**: システムは、稼働状態とバージョンを機械可読な形式で返す確認用の入口を
  提供しなければならない
- **FR-003**: システムは、ブラウザから表示できる最小の画面を配信し、その画面から
  稼働状態を確認できなければならない
- **FR-004**: システムは、動画ファイルの保存場所・待ち受けアドレス・保存データの
  置き場所を、コードを変更せずに設定できなければならない
- **FR-005**: システムは、起動時に保存データを最新の構造へ自動的に適用し、初回起動
  でも手作業を不要としなければならない
- **FR-006**: システムは、停止指示を受けたとき、実行中の処理を安全に終えてから終了
  しなければならない
- **FR-007**: システムは、動作の記録を構造化された形式で出力し、起動・停止・失敗を
  後から追跡できるようにしなければならない
- **FR-008**: システムは、起動に必要な外部ツールが不足している場合、不足している対象と
  対処方法を明示して終了しなければならない

**境界と品質の機械的な担保**

- **FR-009**: リポジトリは、設計文書で定めたモジュール境界に対応する配置を備えなければ
  ならない
- **FR-010**: システムは、ドメイン層が外部入出力（通信・保存・外部プロセス実行）へ直接
  依存する変更を、自動検証で失敗として検出しなければならない
- **FR-011**: リポジトリは、書式・静的検査・自動テストを1つのコマンドでまとめて実行
  できなければならない
- **FR-012**: 共有リポジトリへの変更提案に対して、FR-011 と同じ検証が自動的に実行され、
  結果が提案に紐づいて参照できなければならない
- **FR-013**: 自動検証の失敗は、どの規則に違反したかを出力から特定できなければならない

**前提の実証**

- **FR-014**: リポジトリは、日本語を含む文字列の部分一致検索が追加のミドルウェアなしに
  動作することを確認する自動テストを備えなければならない
- **FR-015**: 前提の実証テストが失敗した場合に検討すべき代替手段が、文書として参照可能で
  なければならない

**開発者向けの導線**

- **FR-016**: リポジトリは、必要な前提ツール・起動手順・検証手順を記した導入手順を
  備えなければならない
- **FR-017**: 本フェーズの進捗と決定は、実行計画として記録・更新されなければならない

### Key Entities *(include if feature involves data)*

- **アプリケーション設定**: 待ち受けアドレス、動画ファイルの探索対象の場所、保存データの
  置き場所、記録の詳細度。実行環境ごとに与えられ、既定値だけでも起動できる
- **保存データの構造バージョン**: 保存先に適用済みの構造の版。起動時の自動適用が参照し、
  適用漏れと将来版の混入を判別する
- **稼働情報**: 稼働状態とアプリケーションの版。確認用の入口から返され、外形監視の
  対象になりうる

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: このリポジトリを初めて触る開発者が、導入手順のみを見てアプリケーションを
  起動できるまでに 15 分以内、実行するコマンドは 1 つである
- **SC-002**: 書式・静的検査・自動テストを含む検証一式が、開発者のローカル環境で 5 分
  以内に完了する
- **SC-003**: ドメイン層の依存方向に違反する変更は、100% 自動検証で失敗し、人手の
  レビューに到達する前に検出される
- **SC-004**: 共有リポジトリへのすべての変更提案で自動検証が実行され、結果が 10 分以内に
  提案上で確認できる
- **SC-005**: 設計文書で定めたモジュール境界（ドメイン・API・保存・メディア解析・スキャン・
  ジョブ）のすべてが、対応する配置としてリポジトリ上に存在する
- **SC-006**: 保存データを削除した状態から再起動しても、手作業なしに 100% 起動が完了する
- **SC-007**: 日本語の部分一致検索の実証テストが、追加のミドルウェアを導入していない
  実行環境で成功する
- **SC-008**: 起動に必要な外部ツールが欠けている環境での起動失敗は、100% 不足対象を
  名指しした表示で終わり、原因不明の失敗にならない

## Assumptions

- 「初期セットアップ」は、[技術選定文書](../../docs/design-docs/tech-stack-selection.md)
  「8. 実装の進め方」の **Phase 0 — 骨組み** を指すものと解釈した。動画の取り込み・一覧・
  再生（Phase 1）、サムネイル・検索・タグ（Phase 2）、認証・バックアップ（Phase 3）は
  本仕様の範囲外とする
- 技術要素（言語・保存基盤・配信方式など）は技術選定文書ですでに決定済みであり、本仕様は
  それを再決定しない。本仕様は「骨組みとして何が満たされていればよいか」のみを定める
- 利用者は単一で、セルフホスト環境（家庭内の1台）での運用を前提とする。認証は Phase 3 で
  扱うため、本フェーズでは未認証で起動する
- 開発環境は Linux または macOS 上のコンテナ実行環境を前提とし、共有リポジトリの自動検証も
  同等の環境で実行される
- 動画ファイルそのものは本リポジトリの管理対象外で、実行環境から参照できる場所に置かれる
- 保存データは再構築可能なインデックスとして扱い、本フェーズではバックアップ手順を定めない
- 本フェーズの成果物に利用者向けの機能は含まれないため、利用者満足度ではなく開発者の
  所要時間と検出率を成功指標とする
