# Phase 0 Research: 現在の機能を前提とした UI の実装

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Date**: 2026-09-13

本機能は「取得できる情報を1つも増やさずに画面を作り込む」ものなので、未確定なのは
**どこに規則を置くか**と**どう検証するか**に集中している。サーバー側の判断は無い。

決定は R-401 から R-412 まで。各項目は Decision / Rationale / Alternatives の 3 点で
書く。

---

## R-401: 見た目の規則（配色・余白・文字）をどこに置くか

**Decision**: `web/src/index.css` の `@theme` に CSS カスタムプロパティとして1か所だけ
定義する。TypeScript 側には同じ値を複製しない。画面と部品はトークン名
（`bg-surface`・`text-body` など Tailwind が `@theme` から生成する実用クラス）だけを使い、
生の色・生の px を書かない。

**Rationale**: FR-001 が求めるのは「規則が1か所にあること」である。Tailwind CSS 4 は
`@theme` に書いた値からそのまま実用クラスを生成するので、CSS を真実にすれば、画面側は
トークン名を使うほかに手が無くなる。値を TS に置いて CSS を生成する案は生成物が増え、
`docs/generated/` と同じ「手編集禁止」の管理対象を1つ増やす。CSS を真実にすれば、
検証（R-405）はそのファイルを読むだけで済む。

**Alternatives considered**:

- **TS のトークン表を真実にし、CSS を生成する**: 型が付く利点はあるが、画面は Tailwind の
  クラス名で書くので結局 CSS 側の名前も要る。二重定義になり FR-001 に反する。
- **Tailwind の既定パレット（`neutral-*`・`sky-*`）をそのまま使い続ける**: いまの状態で、
  明るい背景を前提にした値が画面ごとに散っている。暗い配色へ移すときに拾い漏れが出る。
- **`tailwind.config.ts` の `theme.extend` に書く**: Tailwind 4 では CSS 側の `@theme` が
  推奨の置き場で、いまの `tailwind.config.ts` は走査対象の宣言だけを持つ最小構成である。
  設定の置き場を2つにしない。

## R-402: 暗い配色への移行の範囲

**Decision**: 暗い配色**だけ**を実装する。`:root` に `color-scheme: dark` を宣言し、
明暗の切り替え機構（`prefers-color-scheme` の分岐、切り替えスイッチ）は入れない。
トークン名は色そのもの（`neutral-800`）ではなく役割（`surface`・`surface-raised`・
`body`・`muted`・`accent`・`danger`・`warning`）で付け、将来明るい配色を足すときに
値の差し替えだけで済む形にしておく。

**Rationale**: spec の Assumptions が「画面案の配色（暗い背景）を採用し、明暗の切り替えは
本仕様では扱わない」と決めている。役割名にしておけば、切り替えを足す作業は
「もう1組の値を定義する」だけになり、画面側の書き換えは発生しない。いま分岐を入れると、
使われない側の配色を SC-006（対比 100%）の検証対象として維持し続けることになる。

**Alternatives considered**:

- **`prefers-color-scheme` で両方を用意する**: 検証対象が倍になる。明るい側は誰も見ない
  まま壊れる。
- **色名のトークン（`--color-neutral-850`）にする**: 役割が読み取れず、値を変えるときに
  「この色をどういう意図で使っていたか」が失われる。

## R-403: 一覧へ戻ったときの位置・絞り込み・並び順の復元

**Decision**: 2 段構えにする。

1. **検索語と並び順は URL のクエリに載せる**（`/?q=...&sort=...`）。`react-router` の
   `useSearchParams` で読み書きし、コンポーネントの state を真実にしない。
2. **読み込み済みの項目とスクロール位置は、モジュール内のメモリキャッシュに置く**。鍵は
   正規化したクエリ文字列（`q` と `sort`）。再生画面から戻ったときは、キャッシュされた
   項目をそのまま描いてから `scrollTo` で位置を戻す。キャッシュが無い（全体再読み込み・
   直リンク）場合は 1 ページ目を先頭から読む。

**Rationale**: FR-016 が求めるのは「戻ったときに位置・絞り込み・並び順が保たれる」こと
である。絞り込みと並び順を URL に置くと、戻る／進む・再読み込み・共有のすべてで同じ
一覧が再現でき、追加の保存先が要らない。一方スクロール位置は、無限スクロールで 300 件まで
読んだ状態を URL では表せない。ここを URL に載せる（`page=5` のような形）と、戻るたびに
5 ページ分を読み直すことになり SC-008 の反応時間を損なう。メモリキャッシュなら再取得が
0 回で済み、失われても「先頭から」という妥当な既定に落ちる。

`history.scrollRestoration` はブラウザに任せず `"manual"` にする。無限スクロールでは
復元時点で中身がまだ無く、ブラウザの自動復元は空の文書に対して働いて失敗するためである。

**Alternatives considered**:

- **`sessionStorage` に項目ごと保存する**: 1 ページ 60 件 × 複数ページの JSON を毎回
  直列化することになり、書き込みが重い。得られるのは「タブを閉じても戻れる」ことだけで、
  FR-016 は求めていない。
- **一覧を再生画面の裏で生かしたまま（モーダル再生）にする**: 戻る操作の問題は消えるが、
  再生を URL で開ける（002 で決めた性質）が壊れる。
- **`react-router` の `ScrollRestoration`**: data router（`createBrowserRouter`）が前提で、
  002 が宣言的モードだけを使うと決めている（R-113）。ルータの使い方を広げる判断を、
  画面の作り込みと同じ変更で行わない。

## R-404: 一覧の入口（探す・並べ替える・取り込む）を常に見せる方法

**Decision**: 一覧の上部に `position: sticky; top: 0` の帯を1本置き、そこへ検索欄・
並び順・密度・取り込みをまとめる。帯は背景トークン（`surface`）で塗り、透過させない。
狭い画面では帯の中で 2 行に折り返し、行が増えた分だけ帯が高くなる（重ねない）。

**Rationale**: FR-007 は「スクロール位置によらず常に画面上にある」ことだけを求めている。
`sticky` はスクロール連動の JavaScript を持たないので、SC-008（反応 100ms 以内）に
影響しない。半透過 + `backdrop-filter` は見栄えはよいが、背後の静止画によって文字との
対比が変わり、SC-006（対比 100%）を静的に保証できなくなる。不透明にすれば対比は
トークンの組だけで決まる。

**Alternatives considered**:

- **画面下部の固定バー（モバイル風）**: 指は届きやすいが、デスクトップでは視線の動きが
  大きい。1 つの規則で両方をまかなうほうが FR-001 に沿う。
- **スクロールで隠れ、上方向のスクロールで戻る帯**: 隠れている瞬間があり、FR-007 の
  「常に」を満たさない。

## R-405: 対比 4.5:1 / 3:1 を自動で検証する方法

**Decision**: `web/src/index.css` を読み、`@theme` に宣言された色トークンを取り出して
WCAG の相対輝度から対比を計算する単体テストを置く。検査する組は
[contracts/design-tokens.md](./contracts/design-tokens.md) の対比表に列挙し、テストは
その表と同じ組を検査する。トークンを足しても表に載せなければ検査されないので、表への
追記を規則にする。

**Rationale**: SC-006 は「100%」を求めており、目視では保証できない。色の定義が CSS の
1か所（R-401）にあるので、その 1 ファイルを読めば計算できる。計算式（sRGB → 相対輝度 →
対比）は 20 行程度で、外部の検査ツール（axe・Lighthouse）をビルドに組み込むより軽い。
実行環境のブラウザも要らない。

**Alternatives considered**:

- **axe-core / Lighthouse を CI に入れる**: 実ブラウザと描画が要り、Phase 3 に置いた E2E の
  基盤を先に導入することになる。対比以外の指摘も出るが、それは受け入れ検証（quickstart）で
  人が見る範囲である。
- **表に期待値（計算済みの比）を書いて目視で保つ**: トークンの値を変えたときに表の更新を
  忘れると、嘘の数字が残る。

## R-406: Web の単体テストの実行基盤

**Decision**: **Vitest + Testing Library（`@testing-library/react` / `user-event`、環境は
`jsdom`）** を導入する。`task test-web` はビルド検証に加えて `vitest run` を実行する。
最初の検証対象は、[TD-004](../../docs/exec-plans/tech-debt.md) が名指ししている 3 点
（`useVideos` のカーソル引き継ぎ、検索入力の待ち合わせと打ち切り、再生位置の送信）と、
本機能が新しく作る 3 つの純粋な部品（対比の検査 R-405、表示設定の読み書き R-407、
一覧の復元 R-403）である。

**Rationale**: TD-004 は「次の機能の着手時に、実行基盤と DOM を伴う検証の書き方を同時に
決めて導入する」と契機を明示しており、本機能がその次の機能である。Vitest は既に使って
いる Vite の設定（別名解決・TypeScript）をそのまま使うので、設定は `vite.config.ts` に
`test` の項を足すだけで済む。DOM を伴う検証が無いと、FR-003（狙いを合わせた状態）・
FR-020（キーボードだけで到達）・FR-021（読み上げ向けの代替）は人の手でしか確かめられず、
SC-005 が退行の検出手段を持たない。

**Alternatives considered**:

- **入れない（型検査とビルドのみを続ける）**: 本機能は `web/src/` のほぼ全域に触れる。
  FR-025／SC-009（既存の振る舞いを変えない）を、全域を書き換えながら人の目だけで保証する
  ことになる。
- **Playwright（実ブラウザ）を先に入れる**: 技術選定文書が Phase 3 に置いており、再生の
  E2E という別の目的のものである。起動する対象（Go バイナリ + 実ファイル）も要る。
  本機能が必要とするのは部品単位の検証である。
- **`happy-dom`（`jsdom` より軽い）**: 速いが、`IntersectionObserver` や
  `matchMedia` の再現度で差が出る。どちらも本機能が直接使う。既定の `jsdom` から始め、
  遅さが問題になった時点で差し替える（差し替えは設定 1 行）。

## R-407: 表示設定の保存先と壊れた値の扱い

**Decision**: `localStorage` の単一の鍵 `vv.view.v1` に JSON 1 個で持つ。読み出しは
必ず検証を通し、**鍵が無い・JSON として読めない・値が想定外・`localStorage` 自体が
使えない（プライベートウィンドウ・容量超過）** のいずれでも、例外を外へ出さずに既定値を
返す。書き込みの失敗も無視する（画面は動き続ける）。鍵に版（`v1`）を含め、将来項目を
変えるときは新しい鍵にして古い鍵を読まない。

**Rationale**: FR-018 が「同じ端末の同じブラウザで保たれ、ほかの端末へは持ち越さない」
ことを、FR-019 が「読み出せない・壊れていても既定で表示される」ことを求めている。
`localStorage` は端末とブラウザに閉じており、そのまま FR-018 を満たす。壊れた値で画面が
出ないのは最悪の失敗なので、読み出し側を「絶対に投げない」関数にして、検証を1か所に
集める。版を鍵に含めるのは、移行コードを書かずに済ませるためである（設定が既定へ戻るのは
許容できる損失で、FR-019 がその状態を正常と定めている）。

**Alternatives considered**:

- **`sessionStorage`**: タブを閉じると消える。FR-018 の「開き直したときに保たれる」を
  満たさない。
- **サーバーに保存する**: 利用者ごとの保存には認証が要り、Phase 3 の範囲である。
  FR-024（サーバーとの取り決めを変えない）にも反する。
- **Cookie**: すべての要求に載り、動画配信の要求にも付く。得るものが無い。
- **版を鍵ではなくオブジェクト内の項目に持つ**: 移行コードが要る。設定 2 項目の機能で
  払う代償ではない。

## R-408: 1000 件規模でも反応が鈍らない描き方

**Decision**: 仮想スクロールのライブラリは入れない。一覧の各項目に
`content-visibility: auto` と `contain-intrinsic-size`（枠の見込みの大きさ）を与え、
画面外の項目の描画をブラウザに省かせる。サムネイルは `loading="lazy"` のまま、
`decoding="async"` を足す。

**Rationale**: SC-008 が求めるのは「反応が 100ms 以内に始まる」ことで、DOM の要素数を
減らすこと自体ではない。`content-visibility: auto` はレイアウトと描画を画面外について
省くので、要素数が増えても1フレームの費用が上がりにくい。依存が増えず、R-403 の復元
（`scrollTo` で位置を戻す）とも噛み合う。`contain-intrinsic-size` を与えるのは、省いた
項目の高さを 0 と見積もらせないためで、これが無いとスクロールバーが暴れる。

`content-visibility` に対応しないブラウザでは単に効果が無いだけで、表示は壊れない。

**Alternatives considered**:

- **`@tanstack/react-virtual` などの仮想スクロール**: 1 行の列数が画面幅と密度で変わる
  格子では、列数の計算を自前で持つことになる。スクロール位置の復元（R-403）も仮想化の
  座標系に合わせて作り直しになる。依存も1つ増える。1万件でも「1 ページ 60 件ずつしか
  読まない」ので、実際に DOM に載る数は利用者が読み込んだ分に限られる。
- **何もしない**: 1000 件（約 17 ページ）まで読むと、格子の再レイアウトが目に見えて
  遅くなる。SC-008 に対する根拠が無くなる。

## R-409: 題名の省略と全文の確認手段

**Decision**: 視覚上は 2 行で省略する（`line-clamp-2`）。そのうえで、

- リンクのアクセシブル名は**常に全文**にする（省略は見た目だけで、読み上げには全文が
  渡る）。
- ポインタには `title` 属性で全文を出す。
- キーボードで狙いを合わせた項目は省略を解き、全文を表示する。

**Rationale**: FR-011 は「省略して表示し、全文を確認する手段を持つ」ことを求めている。
`title` 属性だけではキーボードと読み上げに届かず、FR-020・FR-021 を満たせない。3 つを
組み合わせると、どの入力手段からも全文に到達できる。省略を解く際に他の項目の位置が
動かないよう、解けた題名は枠の上に重ねて描く（枠の高さは変えない。FR-005・SC-003）。

**Alternatives considered**:

- **`title` 属性だけ**: 上記のとおり届かない手段がある。
- **常に全文を表示する**: 題名の長さで項目の高さが変わり、格子が崩れる（FR-005）。
- **押すと全文が出る小窓を作る**: 一覧の1件ごとに操作を1つ増やす。得るものに対して
  操作が重い。

## R-410: 「動きを減らす」設定への対応

**Decision**: 装飾的な動き（ホバーの遷移、骨組み表示の明滅、進捗帯の伸び）はすべて
`prefers-reduced-motion` を見る Tailwind の `motion-reduce:` 変種で無効にする。無効に
するのは**動き**だけで、色や不透明度の最終状態は変えない（狙いを合わせた状態が見えなく
ならない。FR-003）。`scrollTo` による復元（R-403）は `behavior: "auto"`（瞬時）で行い、
そもそも動かさない。

**Rationale**: FR-023 が求めるのは装飾的な動きの不適用である。CSS の変種で表現すれば、
判定を JavaScript に持たずに済み、設定の変更にその場で追随する。

**Alternatives considered**:

- **`matchMedia` を読んで JS で分岐する**: 状態を1つ増やし、設定の変更を購読する処理が
  要る。CSS で足りる。

## R-411: 密度を変えたときにスクロール位置を見失わせない方法

**Decision**: 密度は CSS の格子の最小列幅（`grid-template-columns:
repeat(auto-fill, minmax(<最小幅>, 1fr))`）だけを変える。密度を変える直前に、画面の
上端に最も近い項目の id を覚え、変更後にその項目を `scrollIntoView`（`block: "start"`、
瞬時）で画面上端へ戻す。

**Rationale**: US3 の受け入れ 1 は「見ていた動画を見失わない範囲に保たれる」ことを求める。
列幅が変われば 1 行の本数が変わり、同じスクロール座標は別の項目を指す。座標ではなく
**項目**を基準に戻せば、利用者から見た位置が保たれる。列数を JavaScript で計算せずに
済むのは `auto-fill` + `minmax` を使うためで、画面幅への追随（FR-022）も同じ仕組みが
受け持つ。

**Alternatives considered**:

- **スクロール座標を比率で保つ**: 一覧の総高さが変わると、比率が指す項目が変わる。
- **密度ごとに列数を決め打つ**（例: 細かい = 6 列）: 画面幅 360px で 6 列になり FR-022 に
  反する。幅ごとの断りを密度の数だけ書くことになる。

## R-412: 既存の振る舞いを変えていないことの確かめ方

**Decision**: 3 つを併用する。

1. **API を呼ぶ層（`web/src/api/`）には手を入れない**。本機能の変更は
   `pages/`・`components/` と新設する `theme/`・`preferences/` に閉じる。`client.ts` と
   `useVideos.ts` への変更は、R-403 の復元に必要な「キャッシュの差し込み口」だけに限る。
2. **`api/openapi.yaml` を変更しない**。`task generate` の差分検査（`generate-check`）が
   そのまま「契約を変えていない」ことの機械的な証明になる（FR-024）。
3. **002 の受け入れ検証 S1〜S10 を再実行する**（SC-009）。手順は
   [002 quickstart](../002-core-video-library/quickstart.md) のまま使い、本機能の
   quickstart からは参照だけする。

**Rationale**: FR-025／SC-009 は「変わらないこと」を求めており、これは新しい検証を書く
より、**変更の範囲を狭く保って既存の検証をそのまま通す**ほうが確実である。契約を変えない
ことは既に CI が見ているので、証明のために新しい仕掛けを足す必要がない。

**Alternatives considered**:

- **既存の振る舞いを網羅する回帰テストを新規に書く**: 本機能で入れる Vitest の最初の
  対象（R-406）がまさにその一部だが、全域を網羅する版を本機能で書き切るのは範囲を
  超える。狭い変更 + 既存手順の再実行のほうが費用対効果が高い。

## 未確定を残さなかったことの確認

spec の Assumptions で既定が置かれていた 2 点（暗い配色の採用、左の一覧を置かないこと）は
R-402 と Project Structure の決定で受けている。`[NEEDS CLARIFICATION]` は spec・plan の
いずれにも残っていない。
