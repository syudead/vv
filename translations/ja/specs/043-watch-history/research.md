## R-1: 内容の鍵をキーにし、タイトルのスナップショットを持つ `watch_history` テーブル {#r-1-a-watch_history-table-keyed-by-content-key-with-a-title-snapshot}

**決定**: `watch_history` を加える ([data-model.md](data-model.md#migration))。再生ごとに 1 行で、再生したバージョンの `content_key` をキーにし、その時点で表示していたタイトルを持ち、`videos` への外部キーも `playback_progress` へのつながりも持たない。同じパスでの継承は行を新しい内容の鍵に移す。まとめることとまとまりを解くことは行をそのままにする。

| 案 | 判定 |
| --- | --- |
| **独自のテーブル、`content_key`、タイトルのスナップショット** | 採用 |
| `playback_progress` から履歴を導く | 不採用: 内容ごとに 1 行で、保存のたびに上書きされるので、要件 2 と 4 (1 回の視聴に 1 つのエントリ、1 つの動画に複数のエントリ) を満たせない |
| `playback_progress` と同じく、ユーザーキー (まとまりのメンバーには `bundle:<id>`) をキーにする | 不採用: エントリはどのバージョンを再生したかを言えなくなり、まとまりを解いたときにその行をメンバーに返せない。自分の id で開いたメンバーはそのまま再生できる (`GET /api/videos/{id}` はすべてのバージョンを返す) ので、「今の動画を開く」エッジケースはまとまりのキーなしで成り立つ |
| `videos` への外部キー、削除で連鎖 | 不採用: 動画の行は最後の場所がなくなると削除されるが、エッジケースはエントリを残す |

**理由**: エントリは「どの内容を、いつ」に答える。内容の鍵は再スキャンが再現する値なので、戻ってきたファイルはエントリを再び再生できるようにし、タイトルのスナップショットはファイルがない間もエントリを読めるようにする。履歴の行を削除しても他のテーブルには触れない。これが要件 9 である。

## R-2: 1 回の再生に 1 つのエントリ。クライアントが生成する再生 id で識別する {#r-2-one-entry-per-playback-identified-by-a-client-generated-playback-id}

**決定**: `PUT /api/videos/{id}/progress` は省略できる `playbackId` を得る ([contracts/screen-api.md](contracts/screen-api.md#playbackid-on-put-apivideosidprogress))。動画のページは、動画への最初の `play` イベントで id を 1 つ作り、動画 id が変わるか動画が終わりまで再生されるまで、すべての保存とビーコンでそれを送る。最初の再生の前の保存は id を持たない。id は `crypto.getRandomValues()` の 16 バイトから整形した RFC 4122 バージョン 4 の id である: `crypto.randomUUID()` は安全なコンテキストにしかなく、所有者はローカルネットワークの別の端末から平文の HTTP で vv を開ける ([running-vv.md](../../docs/how-to/running-vv.md))。`web/src/player/liveOffset.ts` の `newAttempt` もすでにこれを考慮している。サーバーは一意の `playback_id` に対する `insert or ignore` で、位置と同じトランザクションの中でエントリを挿入するので、一時停止、再開、シークは何も延ばさず、何も作らない。id は `VideoPlayer` ではなくページの再生位置を保存するフックにあるので、プレーヤーの再マウント (エラーからの回復、画質の切り替え) でもエントリは保たれる。プレーヤーが `ended` で送る保存はまだ id を持つ。その後フックが id を捨てるので、終了時のオーバーレイの **Replay**、または終わりからもう一度再生することは、その `play` で新しいエントリを始める。終わりの前の一時停止、シーク、再マウントは id を保つ。

| 案 | 判定 |
| --- | --- |
| **既存の保存に載せるクライアントの再生 id** | 採用 |
| 保存の間の時間の空きでサーバー側でまとめる | 不採用: 同じ動画を再生する 2 つのタブが 1 つのエントリにまとまり (エッジケース)、空きより長い一時停止は 1 回の視聴を分けてしまう (受け入れ条件 3) |
| 最初の再生での別の `POST` | 不採用: 再生ごとに往復が 1 回増え、再生中に所有者がエントリを削除した後、クライアントがそれに気づいて再び送る必要がある。すべての保存に id があれば次の保存がエントリを作り直し、それがエッジケースの「新しいエントリ」である |
| `VideoPlayer` のインスタンスごとの id | 不採用: 回復と画質の切り替えはプレーヤーを再マウントするので、1 回の視聴が分かれる |
| 終わりの後の **Replay** をまたいで id を保つ | 不採用: 終わりに達した視聴は終わっており、もう一度見ることは要件 4 が数える繰り返しの視聴である。id を保つと、それが最初のエントリにまとめられてしまう |
| `crypto.randomUUID()` | 不採用: ローカルネットワークの平文の HTTP では未定義なので、スマートフォンからはエントリが書かれない |

**理由**: 1 回の視聴がどこで始まりどこで終わるかを知るのはクライアント (ページ) だけであり、サーバーは識別以外の何についてもそれを信用してはならない唯一の側である: 時刻とエントリが何を指すかはサーバーが決める。ページを読み直すと新しいエントリが始まる。Issue は「しばらくしてから」の繰り返しの視聴を別のエントリとしており、読み直しと、終わりの後の再生し直しが、ページが観察できる境目である。

## R-3: エントリの時刻は、その id を持つ最初の保存のサーバー時刻である {#r-3-the-entrys-time-is-the-server-time-of-the-first-save-with-its-id}

**決定**: `played_at` は、再生 id を持つ最初の保存でのサーバーの時計である。クライアントはその保存を最初の `play` で即座に送る (今は最初の保存は 5 秒のタイマーか一時停止を待つ) が、プレーヤーが `positioned` を知らせる前には送らない (`web/src/player/VideoPlayer.tsx` の `PlayerStatus.positioned`: 最初のメタデータが届き、再開のシークまたは変換の開始の報告が落ち着いた)。自動再生はソースを設定した直後に `play()` を呼ぶので、最初の `play` は、位置がまだ 0 で、保存された再開位置がまだ適用されていない間に発火しうる。そのときの保存は再開位置を上書きしてしまう。`play` が先に来たとき、フックは id を持ったまま、`positioned` が届いたときに保存を送る。それまでは id を持つ保存もビーコンもないので、その時点で離れても視聴は記録されない。したがって時刻は、メタデータの読み込み、再開のシーク、往復 1 回の範囲で再生の開始である。一覧は `played_at` の降順、次に `id` の降順に並べ、エントリは視聴中もその位置を保つ。

| 案 | 判定 |
| --- | --- |
| **最初の保存のサーバー時刻** | 採用 |
| クライアントが知らせる開始時刻 | 不採用: サーバーが制御しない端末の時計が所有者の履歴を並べることになる |
| 最新の保存の時刻 (最後の活動) | 不採用: 長い視聴は、その間に他の 2 つの視聴があっても先頭に跳ね続ける。「いつ見たか」は始めたときである |
| 開始を位置と別に記録する (位置を書かない保存、または別のリクエスト) | 不採用: ふつう 1 秒未満である再開のシークの時間を得るために、リクエストの形が 1 つ増える。どちらでも端末の時計は並び順に入らない |

## R-4: 既存の再生の記録はマイグレーションが埋める {#r-4-existing-playback-records-are-backfilled-by-the-migration}

**決定**: マイグレーションは `playback_progress` の行ごとに 1 つのエントリを挿入する。`played_at` = その `updated_at`、再生 id はなし、記録の内容の鍵 (まとまりのキーはまとまりの代表に解決する)、その時点で動画のページが表示するタイトル (表示名の上書き、なければファイルのタイトル。内容がライブラリにないときは表示名、なければ空) を持つ。マイグレーションの時点で内容が動画を持たない記録もエントリを得る: 再生位置は内容をキーにするユーザーデータであり、ライブラリからの削除より長く残る (ARCHITECTURE.md、「User data survives a rebuild」。`internal/store` には `playback_progress` の行を削除するものはない)。動画のないエントリは R-5 がすでに示す場合である。埋め戻しは 1 回だけ動くので、それを飛ばすと、内容が戻った後もその視聴は永久に失われる。`video_bundles` の行のない `bundle:<id>` のキーは、そこから内容の鍵を導けないので飛ばす。まとめることと解くことは同じトランザクションでユーザーデータを移す (`internal/store/versions.go`) ので、そのような行は想定しない。

| 案 | 判定 |
| --- | --- |
| **マイグレーションで埋める** | 採用 |
| エントリがないとき、リクエスト時に `playback_progress` を一覧に読み込む | 不採用: 1 つの一覧に 2 つの出どころができ、そのエントリを削除するには再生位置を削除しなければならず、要件 9 に反する |
| 埋めない | 要件 10 により不採用 |

**理由**: SQL だけでこれらの行を作れ、マイグレーションは起動時にリスナーが開く前に 1 回だけ動き、それ以降の履歴の出どころは 1 つになる。

## R-5: 内容がライブラリを離れたエントリは、動画なしで残る {#r-5-an-entry-whose-content-left-the-library-stays-without-a-video}

**決定**: 一覧は各エントリを、その内容の鍵を持ち、所有者が開ける場所を持つ動画に結合する (`visibleVideoCondition`、動画ごとの条件であり、表示される代表の規則ではない)。そのような動画があるとき、エントリはその `Video` を持ち、画面はそれを開く。ないとき、エントリはスナップショットのタイトルだけを持ち、画面はそれを再生できないと示し、リンクを描かない。代表でないまとまりのメンバーもあるとみなすので、そのエントリはそのバージョンを開く。

| 案 | 判定 |
| --- | --- |
| **エントリを残し、再生できないと示す** | 採用 |
| 内容がなくなったエントリを隠す | エッジケースにより不採用: エントリは残り、内容が戻ると再び使えるようになる |
| 再生したバージョンではなく、まとまりの代表に解決する | 不採用: エントリはどのバージョンを見たかを言い、その動画のページが他のバージョンを挙げる |

## R-6: エントリの削除は単純な `DELETE` である。消えたエントリは `404` を返し、画面は読み直す {#r-6-deleting-entries-is-a-plain-delete-a-vanished-entry-answers-404-and-the-screen-reloads}

**決定**: `DELETE /api/watch-history/{id}` は、行があったときは `204` を、なかったときは `404 not_found` を返す。`DELETE /api/watch-history` はすべての行を消し、`204` を返す。どちらもドメインイベントも `/api/events` の通知も発行しない。`404` のとき、画面は表示している一覧が古いので、エラーなしで一覧を先頭から読み直す。それ以外の失敗では行を残し、トーストを出す。

| 案 | 判定 |
| --- | --- |
| **`204`/`404`、`404` で画面が読み直す** | 採用 |
| ない行にも冪等に `204` | 不採用: 画面は自分の一覧が古いことを知れず、エッジケースは一覧を最新にすることを求めている |
| `/api/events` の `watchHistory` 通知 | 不採用: Issue が挙げるタブをまたぐ場面は古い一覧での削除だけであり、それは `404` が覆う。一覧は開いたときに取り直す |

## R-7: 視聴履歴は、既存のゲートの規則に従う所有者専用の画面とルートの 1 つである {#r-7-watch-history-is-one-more-owner-only-screen-and-route-with-the-existing-gate-rules}

**決定**: 画面は `/history` であり、所有者にだけサイドバーの上のグループに挙げ、ゲートの所有者専用のパスに加える (`/history` のゲストは `/login?next=/history` に移る)。3 つのルートは `/api/*` の既定により所有者専用なので、ゲストは他のすべての所有者専用のルートと同じ `401` を受け取る。履歴は外部 API に加えない。

| 案 | 判定 |
| --- | --- |
| **既存の所有者専用のパスとルートの規則** | 採用 |
| 隠した動画と同じく、`/history` のゲストに `404` | 不採用: 画面はすでにゲストを `/settings`、`/tags`、`/duplicates` からログインのページに送っており、受け入れ条件 9 は履歴が表示されないことだけを求めている |

## 改訂: 絞り込み、検索、日付への移動、再開の操作 {#revision-filter-search-date-jump-and-resume-actions}

要件 12 から 18 は、R-1 から R-7 を決めた後に親 Issue に加えた。R-8 から R-13 はその改訂が加える決定である。R-1 から R-7 はそのまま有効である。

## R-8: 絞り込み、検索、日付への移動は一覧の要求の条件である {#r-8-filter-search-and-date-jump-are-conditions-of-the-list-request}

**決定**: `GET /api/watch-history` は `watch`、`query`、`date`、`tz` を得て、ストアはそれらをページの上限より前に SQL で適用する ([contracts/screen-api.md](contracts/screen-api.md#get-apiwatch-history))。画面は読み込んだ行を自分で絞り込むことはない。

| 案 | 判定 |
| --- | --- |
| **一覧の要求の条件** | 採用 |
| 読み込んだページをブラウザーで絞り込み、検索する | 不採用: 要件 6 は履歴の全体を読むので、1 年で 3 つのエントリに一致した絞り込みは、それらを表示するためにすべてのページを読み込むことになる。日付の一覧 (要件 15) も読み込んでいないエントリを必要とする |
| 別の検索のエンドポイント | 不採用: 要件 14 は状態と検索を組み合わせ、2 つの条件を持つ 1 つの要求はライブラリが使う形 (`listVideos`) である |

**理由**: サーバーはすでに順序とページ分けを持つ。条件は同じクエリへの `where` 句の 1 つの追加であり、カーソルは絞り込んだ順序の中を指すので働き続ける。

## R-9: 状態の絞り込みは、ライブラリの規則で動画の今の視聴状態を読む {#r-9-the-state-filter-reads-the-videos-current-watch-state-with-the-librarys-rule}

**決定**: `watch` は `all`、`inProgress`、`watched` のいずれかである (新しいスキーマ `WatchHistoryFilter`)。`inProgress` と `watched` は、動画がライブラリにあり、カードが読むのと同じくユーザーキーで読んだその `playback_progress` の行が `internal/store/listing.go` の `watchCondition` を満たすエントリを残す。動画のないエントリと、動画が未視聴のエントリは `all` の下にだけ現れる (エッジケース)。

| 案 | 判定 |
| --- | --- |
| **動画の今の状態に対する 3 つの値の絞り込み** | 採用 |
| `WatchFilter` を再利用し、`unwatched` に `400` を返す | 不採用: 生成されたクライアントの型が、画面が拒まなければならない値を提示することになり、`unwatched` は 1 回の視聴に対して意味を持たない |
| その視聴 (エントリ) の位置で決める | 要件 12 により不採用: 状態は動画の今のものなので、1 つの動画のすべてのエントリは同じ側に入る |
| 状態をエントリに保存する | 不採用: 状態は保存のたびに変わり、要件 12 はそれをライブラリの「視聴済み」に結び付けている |

**理由**: ライブラリと共有する 1 つの SQL の条件が、視聴済みと示されたカードが `watched` の下に挙がることを保証し (受け入れ条件 10)、ユーザーキーがまとまりの共有の位置をそのカードと揃える。

## R-10: タイトルの検索は、ライブラリのクエリ構文をタイトルだけに使う {#r-10-title-search-uses-the-librarys-query-syntax-on-the-title-alone}

**決定**: `query` は `domain.ParseSearchQuery` で解析し、畳み込んだタイトルに対して `instr` で照合する: 動画を持つエントリでは、その登録された場所のいずれかの `search_key` のタイトルの行と表示名の行 (`locationSearchKey` が作る行で、パスの行を除く)。動画のないエントリでは、スナップショットのタイトルを `search_key` のタイトルの行と同じ照合形 (改行は空白) にした `watch_history.title_key` ([data-model.md、Migration](data-model.md#migration))。タグには照合しない。

| 案 | 判定 |
| --- | --- |
| **ライブラリの構文と照合の形、タイトルの行だけ** | 採用 |
| ライブラリの条件の全体 (`searchExprCondition`) | 不採用: 相対パスとタグ名に一致するので、タイトルにその語がないエントリが挙がり、要件 13 に反する |
| すべてのエントリでスナップショットのタイトルに照合する | 不採用: 名前を変えた動画が古い名前で見つかり、新しい名前で表示される。行は今のタイトルを表示する (ui-design.md、Entry row) |
| タイトルの全文インデックス | 不採用: `location_search_fts` はパスを含むキーの全体をインデックスし、所有者の視聴はライブラリの場所よりはるかに少ないので、`instr` で足りる |

**理由**: 要件 13 が求めるのはライブラリの照合 (部分文字列、NFKC、大文字小文字とかなの畳み込み) であり、ライブラリの対象ではない。解析器と `FoldForMatch` は再利用し、対象は 2 つの名前の行である。名前を変えた動画のファイルのタイトルにある語でもエントリが見つかるが、これは受け入れる: ファイルのタイトルは動画の名前の 1 つである。

## R-11: 日付の一覧と移動は、閲覧者のタイムゾーンでサーバーが計算する {#r-11-the-date-list-and-the-jump-are-computed-on-the-server-in-the-viewers-time-zone}

**決定**: `GET /api/watch-history/dates` は、今の `watch` と `query` の下でエントリのある重複のない日を、新しい順に、画面が送る IANA のタイムゾーン `tz` での `YYYY-MM-DD` として返す。画面は古い日を月にまとめる。一覧の要求での `tz` とともにある `date` (`YYYY-MM-DD` または `YYYY-MM`) は、`played_at` が `tz` でのその日または月の終わりより前のエントリを残し、ページ分けは `nextCursor` で続く。サーバーは `time.LoadLocation` でタイムゾーンを読み込み、タイムゾーンのデータベースのないホストでも応答するように `time/tzdata` を埋め込む。

| 案 | 判定 |
| --- | --- |
| **ブラウザーからの IANA のタイムゾーン、Go で計算する日** | 採用 |
| 分単位の UTC オフセット | 不採用: 1 つのオフセットは夏時間の切り替えの反対側の月では誤るので、1 年にわたる日の一覧は夜遅くのエントリを誤った日に置く |
| 画面が日の境界を計算し、時点 (`before`) を送る | 不採用: 日の一覧はやはりサーバーでタイムゾーンを必要とし、日付の計算をする 2 つの場所は食い違っていく |
| SQL で日ごとにまとめる (`date(played_at / 1000, 'unixepoch')`) | 不採用: SQLite はタイムゾーンを知らない。エントリごとに 1 つの整数を読み、Go でまとめることは所有者の履歴には安価である |
| サーバーが一覧を日と月に分ける | 不採用: どこで日が月になるかは画面の決定であり (`ui-design.md`)、画面はどちらを描くにも日を必要とする |
| 絞り込みと検索を無視した、履歴の全体にわたる一覧 | 不採用: 日付を選ぶと「一致なし」の状態に行き着くことになる。受け入れ条件 13 はエントリのある日付を挙げる |

**理由**: エントリの日は閲覧者がどこにいるかに依存し、それを知るのはブラウザーだけである。サーバーはすべてのエントリを知っている。タイムゾーンの名前を 1 回渡すことで、一覧と移動の両方に 1 つの正本ができる。

## R-12: 絞り込み、検索、日付は画面の URL にある {#r-12-the-filter-the-search-and-the-date-live-in-the-screens-url}

**決定**: `/history` は `watch`、`q`、`date` をクエリパラメーターとして持ち、[list-url.md](../013-library-search/contracts/list-url.md) がライブラリに対してするのと同じく書き、読む (既定は省き、読めない値は既定として扱う)。行のリンクの `state.from` は完全な URL を持つ。

| 案 | 判定 |
| --- | --- |
| **URL のクエリパラメーター** | 採用 |
| コンポーネントの状態 | 不採用: 動画を開くとルートを離れるので、`×` か Esc で戻ると絞り込みと日付が元に戻る |
| `sessionStorage` | 不採用: ライブラリはすでに URL でこれに答えている。2 つ目の仕組みになり、読み直しも共有もできない表示になる |

## R-13: 再開と最初からの操作は動画のページを自動再生で開き、既存の再開の規則が位置を決める {#r-13-the-resume-and-restart-actions-open-the-video-page-with-autoplay-and-the-existing-resume-rule-decides-the-position}

**決定**: 両方の操作 (Issue の `続きから` と `最初から`。英語の語は `ui-design.md` のもの) は、「Play next」と同じく `state: { from, autoplay: true }` で `/videos/{id}` に移動する。その後ページの `resumePosition` が、視聴中の動画を保存した位置から、視聴済みの動画を 0 から始める (要件 18 はその規則を言い直している)。行は `video.progress.positionMs` を `video.durationMs` に対して示す。

| 案 | 判定 |
| --- | --- |
| **既存の状態を通じた自動再生、再開の規則による位置** | 採用 |
| 移動の状態の `startMs` | 不採用: 同じ動画を普通に開いたときと食い違いうる、開始位置の 2 つ目の出どころになる (要件 5 はその規則を保つ)。規則はすでに表示される結果をもたらす |
| 保存した位置の代わりに `resumePosition` を行に示す | 不採用: 要件 16 は今の位置を求めている。2 つが異なるのは `MinResumeMs` (5 秒) 未満のときと、まとまりのメンバーの共有の位置がこのバージョンの長さを超えるとき ([030 R-11](../030-video-versions/research.md)) だけであり、そこでは閲覧者は動画が 0 から始まるのを見る |

**理由**: ページはすでに自動再生と再開の規則を持つので、履歴が加えるのはリンクであり、プレーヤーの機能ではない。
