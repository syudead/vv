# 調査: タグの種類 {#research-tag-kinds}

引き継ぐ決定: タグ、名前、タグの絞り込み ([014 data-model](../014-video-tags/data-model.md))、仮のタグ ([031](../031-tentative-tags/contracts/screen-api.md))、ページ単位のタグの一覧と一括操作 ([036](../036-tag-admin-scale/contracts/screen-api.md))、外部からのタグの管理 ([039](../039-external-tag-admin/contracts/external-api.md))、人物と組織の一覧の絞り込み ([047](../047-video-work-info/contracts/screen-api.md#list-parameters-person-and-organization))。このファイルは、この機能が加える決定だけを記録する。

## R-1: 種類はタグが指す行である {#r-1-a-kind-is-a-row-that-tags-point-to}

**決定**: 種類は新しいテーブル `tag_kinds` に置き、各タグは null を許す `tags.kind_id` を通じてそのうち最大 1 つを指す。

| 案 | 種類の名前の変更や削除 | 同じ名前が 2 回 | 判定 |
| --- | --- | --- | --- |
| **`tag_kinds` の行、`tags.kind_id`** | 1 行が変わる。削除は外部キーで `kind_id` を null にする | 1 つの一意な列 | 採用 |
| `tags` にテキストで持つ種類の名前 | その種類のすべてのタグを書き換える | 表記の揺れが別々の種類になる | 不採用: 要件 4 は種類を単位として名前を変え、削除する |
| 結合テーブル `tag_kind_links` | 1 行が変わる | 1 つの一意な列 | 不採用: タグごとに複数の種類を許し、それは Issue の `対象外` が除いている |

**理由**: `tags` の 1 つの列は「1 つの種類か、なし」をスキーマの性質にし、`on delete set null` はストアの規則なしで要件 4 の「タグは種類なしで残る」を与える。

## R-2: プリセットの種類は特別な扱いのない初期投入の行である {#r-2-preset-kinds-are-seeded-rows-with-no-special-status}

**決定**: マイグレーションは 4 つの種類 `Genre`、`Work`、`Place`、`Character` を挿入する。その後それらは所有者が名前を変えることも削除することもできる普通の種類であり、削除したプリセットは戻らない。

| 案 | 判定 |
| --- | --- |
| **初期投入の行、フラグなし** | 採用 |
| 名前の変更と削除を禁じる `preset` フラグ | 不採用: 要件 4 は所有者に種類の名前の変更と削除を許し、所有者が使わない固定の種類はどの種類のメニューにも残り続ける |
| 保存せず、カタログでキーとして定義するプリセット | 不採用: 画面は英語だけであり ([i18n.md](../../docs/design-docs/i18n.md))、サーバーは保存していないプリセットに対して新しい名前を検査できない (Edge Case "same name twice") |

**理由**: 作品の登場人物は作品そのものと並んでタグ付けされるので、`Character` を Issue の 3 つの例に加える。これ以上のプリセットは、ほとんどの所有者が使わない種類で種類のメニューを埋める。

## R-3: タグの種類はタグの一括操作で設定し、消す {#r-3-a-tags-kind-is-set-and-cleared-through-the-tag-batch}

**決定**: `POST /api/tags/batch` に操作 `setKind` (`kindId` を伴う) と `clearKind` が加わる。1 つのタグも 20,000 のタグも同じルートを通り、どちらの操作も仮のタグを確定しない。

| 案 | 判定 |
| --- | --- |
| **一括操作の `setKind` と `clearKind`** | 採用 |
| `PATCH /api/tags/{id}` の `kindId` | 不採用: 10 個のタグが 10 回の要求と 10 回の部分的な失敗になる (受け入れ条件 2) |
| 新しいルート `PUT /api/tags/kind` | 不採用: 操作を 1 つ増やすために、一括操作の id の上限、重複の除去、3 つの結果の配列を繰り返す |
| null の `kindId` で消す 1 つの `setKind` | 不採用: 生成された Go の型は `kindId` がないことと null であることを区別できないので、フィールドを忘れたクライアントが種類を消してしまう |
| 名前の変更と同じく、種類の設定が仮のタグを確定する | 不採用: Edge Case は仮のタグに種類を保ち、候補に対する一括の種類の変更は候補を見ないまま受け入れてしまう |

**理由**: タグ管理画面はすでにタグを選んで一括操作を適用し (要件 3 の「同じ流れ」)、外部 API は自身の一括操作を通じて同じストアの操作に届く ([039 R-3](../039-external-tag-admin/research.md#r-3-confirm-reject-and-delete-go-only-through-post-apiv1tagsbatch))。

## R-4: どのタグの形も種類の id と名前を持つ {#r-4-every-tag-shape-carries-the-kinds-id-and-name}

**決定**: 画面の API の `Tag`、`TagRef`、`VideoTag` と、外部 API の `Tag` に、オブジェクト `{ id, name }` か null である `kind` が加わる。

| 案 | 判定 |
| --- | --- |
| **`kind: { id, name } \| null`** | 採用 |
| `kindId` だけで、名前は `GET /api/tag-kinds` から | 不採用: タグを表示するどの画面と外部のクライアントも、種類の一覧も読み込む必要がある |

**理由**: そうすると種類の名前の変更がキャッシュしたタグの一覧の文言を変えるので、画面は種類の名前の変更や削除の後にタグの一覧を読み直す (名前の変更はまれであり、読み直しは `refreshTags` としてすでにある)。

## R-5: ライブラリは 1 つのタグの種類で動画を絞り込む {#r-5-the-library-filters-videos-by-one-tag-kind}

**決定**: `person` を受け取る一覧のルートに、1 つの種類の id である `tagKind` が加わる。動画は、そのタグ (手動のもの、またはフォルダからのもの) のどれかがその種類を持つときに一致する。

| 案 | 判定 |
| --- | --- |
| **`tagKind`: その種類のタグをどれか持つ動画** | 採用 |
| 種類はライブラリでタグの選択欄を絞るだけ | 不採用: ライブラリにはタグの選択欄がない。タグはそのチップを押すことで絞り込みに入る ([014 ui-design](../014-video-tags/ui-design.md#active-tag-filters)) |
| 複数の種類を同時に | 不採用: 「どれかの Genre のタグとどれかの Work のタグ」は Issue が問う問いではなく、1 つの値なら絞り込みのチップの行が短く保たれる |

**理由**: 「Work のタグを持つ動画」はカタログ化された動画をそれ以外から分け、この Issue が準備するスマートフォルダの作業はそれを必要とする。パラメータは `person` に従う: 種類のない id は空の一覧になり、種類の一覧は所有者専用なので、ゲストは `guest_filter_not_allowed` を受け取る。

## R-6: 種類の名前は独自の名前空間でタグ名の規則に従う {#r-6-kind-names-follow-the-tag-name-rules-in-their-own-namespace}

**決定**: 種類の名前は `domain.NormalizeTagName` (前後の空白を除去、制御文字なし、1 から 100 コードポイント、完全一致) で検査し、種類の間でだけ一意である。タグと種類は同じ名前を持ってよい。

| 案 | 判定 |
| --- | --- |
| **タグの規則、独自の名前空間** | 採用 |
| タグ名と共通の 1 つの名前空間 | 不採用: 種類 `Work` がタグ `Work` を妨げ、両者が同じ一覧に表示されることはない |
| 大文字と小文字を区別しない一意性 | 不採用: タグ名は大文字と小文字を区別し ([014 data-model、名前の規則](../014-video-tags/data-model.md#name-rules))、2 種類の名前に 2 つの規則があれば所有者を驚かせる |

**理由**: 規則を再利用すると、その 3 つの `reason` の値も再利用するので、画面と外部のクライアントは不正な種類の名前を不正なタグ名と同じように扱う。

## R-7: 種類は名前だけを持つ {#r-7-a-kind-has-a-name-and-nothing-else}

**決定**: 種類は色もアイコンも保存しない。`design` 段階は既存のトークンと種類の名前で種類を区別する。

| 案 | 判定 |
| --- | --- |
| **名前だけ** | 採用 |
| 種類ごとに所有者が選ぶ色 | 不採用: 選択欄と両方のテーマでのコントラストの検査が必要になり、Issue の `UI品質` は種類をタグ名より従の位置に保つ |

## R-8: タグの一覧は 1 つの種類か、種類なしで絞り込む {#r-8-the-tag-list-filters-by-one-kind-or-by-no-kind}

**決定**: `GET /api/tags` は、種類の id か `none` である `kind` を受け取る。`q`、`tentative`、`unused` と AND をとる。

| 案 | 判定 |
| --- | --- |
| **1 つの値、id か `none`** | 採用 |
| 複数の種類 | 不採用: 受け入れ条件 1 は 1 つの種類と種類なしを求めている。複数の値の絞り込みは、どの要件のためでもなくチップとメニューの状態を加える |
