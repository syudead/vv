# 調査: ドラッグ&ドロップで並べ替え、グループにし、統合し、まとめる {#research-drag-and-drop-to-reorder-group-merge-and-bundle}

引き継ぐ決定: グループ、その項目、入れ子、解散、`group` イベント ([048 の調査](../048-groups/research.md))。バージョンのまとまりとユーザーキー ([030 データモデル、User key](../030-video-versions/data-model.md#user-key))。`@dnd-kit` によるドラッグでの並べ替え ([044 R-9](../044-playlists/research.md#r-9-drag-reordering-with-dnd-kitcore-and-dnd-kitsortable))。このファイルは、この機能が加える決定だけを記録する。

## R-1: 取り消しは操作が変えた行を戻し、その行はサーバーが持つ {#r-1-undo-restores-the-rows-the-operation-changed-held-by-the-server}

**決定**: 各ドラッグ操作は、自分のトランザクションの中で、変えようとしている行 (変更前イメージ) と、変更後の同じ行 (変更後イメージ) を読む。取り消しは、今の行がまだ変更後イメージと等しいときに変更前イメージを書き戻し、そうでなければ全体として失敗する。

| 案 | 統合したか解散したグループを、その id、お気に入り、プレイリストの項目とともに戻す | 別の場所での変更を検出する | 判定 |
| --- | --- | --- | --- |
| **行イメージ、変更後イメージで守る** | はい | はい、正確に | 採用 |
| クライアントからの逆の呼び出し (加えたものを取り除き、取り除いたものを加える) | いいえ: 削除したグループは新しい id で、お気に入りとプレイリストの項目なしで戻る | いいえ | 不採用 |
| 取り消しの前に `groups.updated_at` を比べる | はい | まとまり、お気に入り、プレイリストでは検出しない。1 ミリ秒の中の 2 回の書き込みは等しく見える | 不採用 |
| 永続する履歴のテーブル | はい | はい | 不採用: 取り消しはそのトーストの間だけ生きる (要件 12、エッジケース) ので、再起動を越えて残る必要のあるものはない |

**理由**: 統合 (要件 8)、最後の項目の取り除き、まとめることは、どの公開ルートも作り直せない行を削除するので、それを戻せるのはサーバーだけである。変更後イメージ全体を比べることが、エッジケース「別の画面で変わった」の求めるものであり、操作が書いたすべてのテーブルを扱う。

## R-2: 取り消しの記録は `internal/app` のメモリに 10 分間置く {#r-2-the-undo-journal-lives-in-internalapp-in-memory-for-10-minutes}

**決定**: `app.Organizer` は各操作のイメージをランダムなトークンの下に 10 分間、最大 100 件保ち、トークンは使われたら忘れる。クライアントは、トーストが閉じるか画面が変わるとそれを忘れる。

| 案 | 判定 |
| --- | --- |
| **`internal/app` のメモリ上** | 採用 |
| `internal/store` のメモリ上 | 不採用: ストアはトランザクションを実行するアダプターであり、トークンの寿命はユースケースの規則である |
| イメージをクライアントに送り、送り返させる | 不採用: 20000 項目のグループの統合はグループ全体を 2 回送り、サーバーは自分が書いていないイメージを検証しなければならなくなる |

**理由**: イメージはストアが書いて読む不透明なバイト列なので、アプリケーション層はストアを import せずにそれを持てる ([ARCHITECTURE.md、Intended dependency direction](../../ARCHITECTURE.md#intended-dependency-direction))。クライアントの寿命の方が短いので、サーバーの 10 分はメモリを抑えるだけである。

## R-3: ドラッグ操作ごとに 1 つのルート、それぞれ 1 つのトランザクション {#r-3-one-route-per-drag-operation-each-in-one-transaction}

**決定**: 並べ替え、移動、グループ作成、統合、まとめは `/api/organize/` の下の新しいルートで、それぞれが変更全体 (移動の取り除きと追加、グループの作成と親の中でのその場所) を 1 つのトランザクションで実行する ([contracts/screen-api.md](contracts/screen-api.md))。

| 案 | 判定 |
| --- | --- |
| **新しい複合ルート** | 採用 |
| クライアントから既存のグループのルートを続けて呼ぶ | 不採用: 移動は取り除きと追加になるので、その間の失敗で項目が失われ、取り消しには 2 つの記録が要る |
| 操作のフィールドを持つ 1 つのルート | 不採用: 5 つの本文は応答のトークンのほかに何も共有せず、生成したクライアントはそれらの型を失う |

**理由**: エッジケース「保存が失敗した」は操作の前の状態を求め、それを与えるのは 1 つのトランザクションだけである。

## R-4: ドラッグしたカードは、動画とグループの id で画面の順に指す {#r-4-dragged-cards-are-named-by-video-and-group-id-in-screen-order}

**決定**: どの操作も、ドラッグしたものを動画の id かグループの id を持つ `{kind, id}` として、カードが画面に現れる順に指し、カードをドラッグして出したグループを `from` として指す。

| 案 | 判定 |
| --- | --- |
| **動画とグループの id と `from`** | 採用 |
| グループのページではグループの項目の id、ほかでは動画とグループの id | 不採用: 1 つの操作に 2 つの形ができ、ライブラリとフォルダの画面には項目の id がない |

**理由**: ライブラリとフォルダの画面は動画とグループの id しか知らない。`from` があれば、追加と同じように、サーバーはそのグループの中の項目をユーザーキーとグループの id で見つけられる ([048 データモデル、Edits](../048-groups/data-model.md#edits))。画面の順は、2 つ目のフィールドなしで要件 11 の相対的な順序を保つ。

## R-5: 統合は、ドロップしたグループのお気に入り、プレイリストの項目、親を対象に渡す {#r-5-a-merge-hands-the-dropped-groups-favorites-playlist-items-and-parents-to-the-target}

**決定**: X を Y に統合すると、X の項目を順に Y に付け加え、X がお気に入りだったときは Y をお気に入りにし、すべてのプレイリストとすべての親グループで X を X の位置にある Y に置き換え、それから X を削除する。Y がすでにそこにあるところ、または Y が自分自身の祖先になるところでは、代わりに X の項目を取り除く。

| 案 | 判定 |
| --- | --- |
| **親は Y とともにその場所を保つ** | 採用 |
| 解散と同じように、親が X を失う | 不採用: 要件 8 はお気に入りとプレイリストで X を Y に置き換える。X を持っていた親がそれを失うと、そこが統合が空にする唯一の場所になる |

**理由**: 親グループはお気に入りやプレイリストの項目と同じ種類の参照なので、要件 8 の規則に従う。統合した自動のグループは、解散と同じように、そのフォルダに `ungroup` を書く ([048 R-4](../048-groups/research.md#r-4-dissolving-deletes-the-group-for-an-automatic-group-it-writes-ungroup))。

## R-6: 「Make a group」は新しいグループを対象があった場所に置く {#r-6-make-a-group-puts-the-new-group-where-the-target-was}

**決定**: 新しいグループは対象の動画を先頭に、ドラッグした動画をその後に画面の順で持ち、対象のタイトルを 100 文字に切ったものを名前とし、グループのページでは対象の項目の位置を取る。そのとき対象とドラッグした項目はそのグループを離れる。

| 案 | 判定 |
| --- | --- |
| **対象が先頭、対象の場所に置く** | 採用 |
| ドラッグした動画が先頭 | 不採用: その場にとどまるのは対象のカードなので、グループは「対象と、そこに加わったもの」と読める |
| 新しいグループを親の末尾に付け加える | 不採用: 要件 5 はそれを元の位置に置く |

**理由**: ライブラリとフォルダの画面では、新しいグループは親を持たず、ライブラリの最上位のグループの中に現れる ([048 R-6](../048-groups/research.md#r-6-the-library-top-level-and-partial-search-matches-over-descendants))。

## R-7: カードと行のための、`@dnd-kit` による 1 つのドラッグ層、上と間 {#r-7-one-drag-layer-on-dnd-kit-for-cards-and-rows-over-and-between}

**決定**: `web/src/videoList` の共有のドラッグ層が、グリッドと一覧のために既存の `@dnd-kit` パッケージを包む: ポインターがカードの中央の上にあるとそのカードにドロップし、先頭側か末尾側の端の近くでは、並べ替えが許される場所でカードの間にドロップし、`DragOverlay` がドラッグしたカードを選択数とともに示す。

| 案 | 判定 |
| --- | --- |
| **`videoList/reorder.tsx` の `@dnd-kit` の設定を拡張する** | 採用 |
| ネイティブの HTML のドラッグ&ドロップ | 不採用: 電話でタッチイベントがない (要件 14) |
| グリッドのドラッグのための 2 つ目のライブラリ | 不採用: `@dnd-kit` は独自の衝突判定の規則でグリッドをすでに扱え、1 つの画面の 2 つのドラッグの仕組みはポインターを奪い合う |

**理由**: 画面は仮想化されていないので、どのカードもマウントされたドロップ先である。センサーは `useReorderSensors` のものだが、クリックやホバーでのスクラブがドラッグを決して始めないように、カードには 4 px ではなく 8 px のポインターの移動が要る (`UI品質`)。タッチは 200 ms の押下を保ち、スワイプはスクロールに残る。キーボードの利用者は、並べ替えには一覧表示のハンドルを、ほかのすべてには 048 のメニューを引き続き使う。表示の見た目は `ui-design.md` が決める。

## R-8: 画面は操作をすぐに適用し、失敗したら元に戻す {#r-8-the-screen-applies-an-operation-at-once-and-puts-it-back-on-failure}

**決定**: 画面はサーバーが応答する前にドロップの結果を示す。失敗するとドロップの前に示していたものを戻して操作が失敗したと伝え、成功すると取り消しのトーストを示す。

| 案 | 判定 |
| --- | --- |
| **すぐに適用し、失敗したら戻す** | 採用 |
| サーバーを待ってから結果を示す | 不採用: 往復の間、カードが古い場所に跳ね戻る |

**理由**: グループのページの並べ替えはすでにこう動いており (`groups/useGroupEdits.ts`)、`group` イベントがその後にサーバーの状態を読む ([048 R-13](../048-groups/research.md#r-13-a-group-event-tells-open-screens-to-read-again))。

## R-9: 取り消しのトーストは、アクションを持つ既存のトーストである {#r-9-the-undo-toast-is-the-existing-toast-with-an-action}

**決定**: `ui/Toast.tsx` の `useToast` は任意のアクション (ラベルとハンドラー) とそのための表示時間を得て、取り消しのトーストはそれらを使う。

| 案 | 判定 |
| --- | --- |
| **既存のトーストのアクション** | 採用 |
| 別の取り消しのバー | 不採用: 2 つ目の通知の場所は、シェルがすでに幅に応じて置いているトーストの積み重ねと競合する |
