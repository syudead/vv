# 調査: 中身が保存した条件に従うスマートフォルダ {#research-smart-folders-whose-contents-follow-a-saved-condition}

親 Issue: #1139。グループ、その再生の順序、見え方、ライブラリの項目のクエリーは [048 調査](../048-groups/research.md) と [048 データモデル](../048-groups/data-model.md) から、部分的に合うグループは [027 library-api.md](../027-partial-group-search/contracts/library-api.md) から、タグの種類は #1136 (`specs/051-tag-kinds/`、この計画を書いた時点ではレビュー中) から引き継ぐ。ライブラリの絞り込みは `domain.VideoQuery` と、`internal/store/listing.go` と `internal/store/library_items.go` にあるその SQL である。このファイルは、この機能が加える決定だけを記録する。

## R-1: スマートフォルダはグループではなく、独自のエンティティである {#r-1-a-smart-folder-is-its-own-entity-not-a-group}

**決定**: スマートフォルダは、新しいユーザーデータのテーブル `smart_folders` にあり、独自の id、規則、並び順、親を持つ ([data-model.md、Migration](data-model.md#migration))。お気に入り、プレイリスト、ライブラリ、動画のページは、`video` と `group` と並ぶ `smartFolder` の種類でそれを指す。

| 案 | 判定 |
| --- | --- |
| **独自のテーブルと種類** | 採用 |
| 規則を持つ `groups` の行 | 不採用: グループは項目を持ち、その動画をライブラリの最上位から外し、`group_items` を通して入れ子になる。スマートフォルダはそのどれもしない (要件 3、5、7) ので、グループのすべての読み書きが種類で分岐することになる |

**理由**: Issue はスマートフォルダを、動画を決して移動しない仮想の見え方とし、グループは動画が実際にある場所である。両者を分けておけば、048 のグループの規則は手付かずのままになる。

## R-2: 中身は保存せず、読むときに計算する {#r-2-contents-are-computed-when-read-not-stored}

**決定**: スマートフォルダの中身は、フォルダの実効の規則で実行したライブラリの項目のクエリーである。所属については何も書かない。

| 案 | 判定 |
| --- | --- |
| **読み取りのときに評価する** | 採用 |
| 変更のたびに更新する所属のテーブル | 不採用: 条件に合うかを変えうるすべての書き込み (タグ、クレジット、進捗、お気に入り、まとめること、取り込み) がそれを更新しなければならず、書き込みを 1 つでも漏らすと、次に全体を更新するまで誤ったメンバーが残る |
| 所属を作り直すバックグラウンドのジョブ | 不採用: ジョブが動くまでフォルダは条件に遅れ、受け入れ条件 1 に反する |

**理由**: そうすれば要件 3 は、何が情報を書いたかにかかわらずすべての読み取りで成り立ち、取り込みが規則を待つことはない (数万本の動画についてのエッジケース)。開いている画面にもう一度読むよう伝えることは、別の通知である ([R-12](#r-12-writes-that-can-change-a-match-publish-smartfolderschanged))。

## R-3: 規則はライブラリの絞り込みの項目であり、中身は絞り込んだライブラリである {#r-3-a-rule-is-the-library-filters-fields-contents-are-the-filtered-library}

**決定**: 規則は、ライブラリの絞り込みの項目 (検索の文言、視聴の状態、再生できるものだけ、お気に入りだけ、タグ、タグの種類、人物、組織、追加日の範囲、長さ) を持ち、そのどれもが成り立たなければならない。フォルダの中身は、その絞り込みで `ListLibrary` が返すものとちょうど同じである: どのグループにも入っていない動画、見える動画のすべてが合うときは 1 枚のカードとしてのグループ、部分的に合うグループの合う動画 (027、048 R-6)。

| 案 | 判定 |
| --- | --- |
| **ライブラリの絞り込みとライブラリの項目のクエリー** | 採用 |
| OR、NOT、入れ子の句を持つ式の木 | 不採用: 条件の UI はライブラリの絞り込みの言葉と部品を使わなければならず (`UI品質`)、検索の文言はすでに `OR` と `-` を受け付ける |
| 動画のいずれかが合うときにグループを示す | メンテナーが不採用とした (2026-10-15): フォルダは絞り込んだライブラリが示すものを示す (要件 4、受け入れ条件 3) |

**理由**: 要件 4 と受け入れ条件 5 は、フォルダが絞り込んだライブラリと等しいことを求める。同じクエリーを呼べば、それは作りの上で成り立ち、コードを写すことに反する規則 (AGENTS.md) にも従う。

## R-4: ライブラリの絞り込みに追加日の範囲と長さが加わる {#r-4-the-library-filter-gains-added-within-and-length}

**決定**: `VideoQuery` とライブラリの URL に、`addedWithin` (日数、1 から 36,500: 今からその日数を引いた時点以降に追加された) と、`minDuration` と `maxDuration` (秒、両端を含む。長さが分からない動画はどちらにも合わない) が加わる。ゲストの一覧が明かさないものを何も明かさないので、ゲストもそれらを使える。

| 案 | 判定 |
| --- | --- |
| **共有の絞り込みに加える** | 採用 |
| スマートフォルダだけ | 不採用: 条件の編集画面にライブラリにない部品が要り、保存した絞り込みがそれらを持ち帰れない (要件 10) |
| 追加日の絶対的な日付の範囲 | 不採用: 固定の範囲には新しい動画が決して加わらないので、満たされ続けるフォルダではなく一度きりの絞り込みになる |

**理由**: 要件 2 は、規則が使う情報として追加日と長さを挙げる。

## R-5: 子の実効の規則は、その経路上のすべての規則の AND である {#r-5-a-childs-effective-rule-is-every-rule-on-its-path-anded}

**決定**: スマートフォルダの親は多くても 1 つである。その実効の規則は、自身の規則とすべての祖先の規則である。ストアは各規則の絞り込みの条件を順に適用するので、2 つの階層が両方とも人物や視聴の状態を挙げてよい。フォルダのページは、その子を名前順に先に挙げ、続いてその中身を挙げる。

```mermaid
flowchart LR
  root["猫 (タグ)"] --> child["未視聴 (視聴)"]
  child --> eff["中身: タグ 猫 AND 未視聴"]
```

| 案 | 判定 |
| --- | --- |
| **経路に沿った AND、階層ごとに適用** | 採用 |
| 規則を 1 つの `VideoQuery` にまとめる | 不採用: 2 つの階層の単一の値の項目 (人物、組織、タグの種類、視聴) はまとめられず、衝突にはそれ専用の規則が要る |
| グループの項目のように、手で入れる子 | 不採用: Issue は中身が条件だけに従うことを求める (`対象外`) |

**理由**: 要件 7 は、子を両方の条件に合うものと定める。条件を階層ごとに適用すれば、どの項目でも「親の中身をもう一度絞り込んだもの」がそのまま成り立つ。

## R-6: 動画はフォルダの並び順に従い、random は拒む {#r-6-videos-follow-the-folders-sort-random-is-refused}

**決定**: フォルダは `random` 以外のライブラリの並び順の 1 つ (既定は `addedDesc`) を保存し、その中身はその順で挙げ、再生する。グループのカードは、ライブラリと同じようにその値で並ぶ。

| 案 | 判定 |
| --- | --- |
| **保存したライブラリの並び順** | 採用 |
| `random` | 不採用: 順序が読み取りのたびに変わるので、`Up next` とメンバーの窓が 2 つの要求の間で食い違う |

## R-7: 最上位のスマートフォルダは、絞り込みのないライブラリのカードである {#r-7-root-smart-folders-are-cards-in-the-unfiltered-library}

**決定**: ライブラリの最上位は、親のないすべてのスマートフォルダを、グループと動画の中のカードとして挙げ、グループのカードと同じようにその値で並べる。その動画も挙げたままである。検索か絞り込みがあるときはスマートフォルダのカードを除くが、お気に入りだけはお気に入りにしたものを挙げる。

| 案 | 判定 |
| --- | --- |
| **絞り込みのないライブラリのカード** | 採用 |
| 中身のすべてが合うときは、絞り込みがあってもカードにする | 不採用: フォルダの中身のすべてが別の絞り込みに合うことはまれで、その確認には、絞り込んだ読み取りのたびにフォルダごとに 1 回の評価がかかる |
| 別の一覧にだけ示す | メンテナーが不採用とした (2026-10-15): 要件 6 はそれらをグループと動画に混ぜる |

**理由**: 要件 5 は動画をその場所に保ち、要件 6 はフォルダをその隣に置く。絞り込んだライブラリは動画の検索であり、それにはフォルダの動画がすでに答える。

## R-8: 空のフォルダは残り、所有者にだけ示す {#r-8-an-empty-folder-stays-and-is-shown-to-the-owner-only}

**決定**: 見える中身がないフォルダは、所有者には挙げて開け、ゲストには示さない (開くと `404`)。048 の見え方と同じである。

| 案 | 判定 |
| --- | --- |
| **所有者は見て、ゲストは見ない** | 採用 |
| 空のグループと同じように、全員から隠す | 不採用: 所有者がそれを開いて条件を変えられない (合う動画が 0 本のときのエッジケース) |

## R-9: 統合は規則を書き換え、削除された参照は規則を何にも合わなくする {#r-9-merges-rewrite-rules-a-deleted-reference-makes-the-rule-match-nothing}

**決定**: タグ、人物、組織の統合は、統合元の id を挙げるすべての規則を、統合のトランザクションの中で統合先の id に書き換える。もう存在しないタグ、タグの種類、人物、組織を挙げる規則は何にも合わず、その子孫も同じである。所有者の読み取りは存在しない参照を挙げる。

| 案 | 判定 |
| --- | --- |
| **統合で書き換え、存在しない参照では何にも合わない** | 採用 |
| ライブラリが存在しないタグを落とす (`MissingTagIDs`) のと同じように、存在しない項目を落とす | 不採用: タグが削除されたフォルダ `タグ: 猫` がすべての動画を挙げ、エッジケースが求めること (`効かないと分かる`) と違う |
| 参照ごとの外部キー | 不採用: 参照は JSON の規則の中にあり ([data-model.md](data-model.md#smart_foldersrule))、それは常に丸ごと読む |

## R-10: `owner_kept` は所有者のフォルダを記録する {#r-10-owner_kept-records-the-owners-folders}

**決定**: `smart_folders.owner_kept` は、所有者が作ったフォルダでは 1 で、その名前、規則、並び順、親への所有者のすべての書き込みが 1 に設定する。それを設定せずにフォルダを作るのは、AI による整理の Issue が加える書き込みの経路だけになる。

| 案 | 判定 |
| --- | --- |
| **所有者の書き込みが設定するフラグ** | 採用 |
| `created_by` の値 | 不採用: 要件 11 は、所有者が条件を変えた AI のフォルダも所有者のものとして数えることを求める |

## R-11: 規則は所有者の情報を読み、見え方は閲覧者のものである {#r-11-the-rule-reads-the-owners-facts-visibility-is-the-viewers}

**決定**: 規則は、誰がフォルダを見るかにかかわらず、所有者のタグ、進捗、お気に入り、完全な検索で評価する。その結果を、閲覧者が見てよいものに切り詰める (048 の見え方)。

| 案 | 判定 |
| --- | --- |
| **所有者の情報、閲覧者の見え方** | 採用 |
| 閲覧者として規則を評価する | 不採用: ゲストの絞り込みはタグ、クレジット、視聴の状態、お気に入りを拒む (`guest_filter_not_allowed`) ので、ゲストは違うフォルダを見ることになる |

## R-12: 条件に合うかを変えうる書き込みは `SmartFoldersChanged` を発行する {#r-12-writes-that-can-change-a-match-publish-smartfolderschanged}

**決定**: 新しいドメインイベント `SmartFoldersChanged` (画面のイベントの種類は `smartFolder`) は、中身かカードが変わったかもしれないフォルダを挙げる。フォルダの編集はそのフォルダとその子孫を挙げる。いずれかの規則に合う動画を変えうる、コミットされた書き込みはすべてのフォルダを挙げ、フォルダが 1 つもないときは何も発行しない ([data-model.md、Notices](data-model.md#notices))。進捗の保存は、動画の視聴状態を変えるときだけ発行する。

| 案 | 判定 |
| --- | --- |
| **すべてのフォルダを挙げる 1 つの通知** | 採用 |
| 編集だけ | 不採用: 新しくタグを付けた動画が、再読み込みするまで、開いているフォルダにもライブラリのフォルダのカードにも現れない (受け入れ条件 1) |
| 書き込みがどのフォルダを変えたかを割り出す | 不採用: 書き込みのたびにその前後ですべての規則を評価することになる。それは [R-2](#r-2-contents-are-computed-when-read-not-stored) が書き込みの経路から外す費用である |
| `group` イベントを再利用する | 不採用: グループとスマートフォルダの id は別の空間である |
| 進捗の保存のたびに発行する | 不採用: 進捗は再生中に数秒ごとに保存され、通知のたびにライブラリは読み込んだページを読み直す |

## R-13: 20,000 本の動画と 50 個のスマートフォルダでの読み取りの予算 {#r-13-a-read-budget-at-20000-videos-and-50-smart-folders}

**決定**: 20,000 本の動画で、50 個の最上位のフォルダがある絞り込みのないライブラリの最初のページと、3 階層の深さのフォルダのページは、それぞれ 500 ms 以内に返る。これをストアのベンチマークで測る。

| 案 | 判定 |
| --- | --- |
| **予算を明示したベンチマーク** | 採用 |
| 単体テストの中の時間制限 | 不採用: CI のランナーはばらつき、時間の検証はコードの変更なしに失敗する |

**理由**: ライブラリのページは最上位の各フォルダのカードの値を計算し、フォルダごとに 1 回規則を評価する。`BenchmarkRebuildFolderIndex` は、フォルダの索引に同じ種類の予算を設けている。
