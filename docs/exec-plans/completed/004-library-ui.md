## 目的

002 で入った機能（一覧・検索・並べ替え・取り込み・再生・視聴状況）はそのままに、
**見た目の規則を 1 か所に集める**。色と形と大きさは `web/src/index.css` の `@theme` を
唯一の真実とし、生の色と Tailwind 既定のパレット名を `web/src/**/*.tsx` から締め出す
（FR-001）。あわせて、対比・表示設定・一覧の復元・視聴状況の読み替え・既存の 3 点を
機械で確かめられる状態にする（SC-006・SC-007・SC-009）。

既存の振る舞いは変えない（FR-025）。`web/src/` のほぼ全域を書き換えるため、これを人の目
だけで保証することはできない。そこで本機能で Vitest + Testing Library を導入し
（[TD-004](../tech-debt.md) が名指しした契機がこの機能である）、書き換えの**前に**回帰の
網を張る。

## 決定の記録

### Vitest は 5.x、`defineConfig` は `vitest/config` から取る（T003）

`web/vite.config.ts` の `defineConfig` を `vite` ではなく `vitest/config` から取るように
変えた。Vite 側の `defineConfig` は `test` の項を型として知らず、`make lint-web`
（`tsc --noEmit`）が落ちるためである。実行時の振る舞いは変わらない。

あわせて `web/tsconfig.json` に 2 つ足した。`types` の `vitest/globals`（T003 が
`globals: true` を指定しているので、Phase 2 以降のテストが `describe`／`it`／`expect` を
import せずに書ける）と、`include` の `vitest.setup.ts`（型検査の対象に入れる）である。

### `passWithNoTests: true` を置いた（T003）

当時の実装計画が「テストが0件でも成功で終わる」ことを求めているため。
テストが揃う Phase 2 以降は外してよい。`web/vite.config.ts` の当該行にその旨を書いてある。

### 増えた依存は開発時の 4 つだけ（T002・plan の G2）

`vitest`・`@testing-library/react`・`@testing-library/user-event`・`jsdom` を
`devDependencies` に足した。`dependencies`（実行時の依存）は 1 つも増えていない。

### 対比表に `surface-sunken` の 2 組を足した（T017）

サムネイル未生成の枠（`bg-surface-sunken`）に理由の文言を置くので、`muted` と `body` を
その地の上に描くことになった。[contracts/design-tokens.md](../../../specs/004-library-ui/contracts/design-tokens.md)
2. の対比表は「表に無い組は検査されない」と定めているため、`muted` / `surface-sunken`
（9.20）と `body` / `surface-sunken`（16.81）を表と `web/src/theme/tokens.test.ts` の
両方に足した。トークンの値は変えていない。

### `takeListSnapshot` は控えを消さない（T027）

名前は「取り出す」だが、読んでも控えは残す実装にした。React は開発時に効果と
`useState` の初期化を 2 回走らせるので、1 回目で消すと 2 回目で復元が消える。
要らなくなった控えは次の `saveListSnapshot` が上書きするか、取り込み完了時の
`clearListSnapshot` が捨てるので、残しても溜まらない（持つのは常に 1 件）。

### 鍵の正規化は「並び順の既定値」も吸収する（T027）

`/` と `/?sort=addedDesc` は利用者から見て同じ一覧なので、鍵も同じにした。
`defaultSort`（`addedDesc`）を `web/src/api/listSnapshot.ts` にも置いてある。

T037 で `web/src/pages/LibraryPage.tsx` の同名の定数は無くなった（並び順の既定値は
`web/src/preferences/viewPreferences.ts` の `defaults.sort` が持つ）。一覧は常に
確定した並び順を鍵として渡すので、`listSnapshot.ts` 側の既定値は「`sort` を省いて
呼んだとき」だけに効く保険になっている。

### 復元の判定は「鍵ごと」覚える（T029）

`web/src/api/useVideos.ts` に足したのは初期状態の受け渡し口だけである
（[R-412](../../../specs/004-library-ui/research.md) が範囲を限定している）。
「復元で埋めたかどうか」を 1 回で消える印にせず、並び順・検索語・読み直しの世代を
そのまま覚える形にした。効果が何度走っても同じ判断になり、開発時の 2 回実行で
復元が捨てられない。カーソルの引き継ぎ・打ち切り・`reload` は変えていない
（`web/src/api/useVideos.test.ts` が変更前と同じ内容で通っている）。

### `noRawColors.test.ts` の猶予の一覧を畳んだ（T024〜T026）

`pages/VideoPage.tsx` が唯一の猶予だった。書き換えが済んで一覧が空になったので、
「一覧が空になったらこの仕組みごと消してよい」という当該ファイルの取り決めに従い、
`pendingRewrite` と対になる検査を消した。以後は走査対象のすべてが同じ規則で検査される。

### 取り込みの「新しさ」は id で見分ける（T030 の付随）

`GET /api/scans/current` は実行中のものが無ければ**最後に終わったもの**を返す。したがって
`ScanStatus` は「終わっている取り込みがある」としか言えず、最初の巡回で `done` を読んだ
だけで `onFinished` を呼んでいた。一覧を開くたびに起きるので、T030 の復元は毎回その場で
捨てられていた（控えを消し、`reload()` が項目を空にする）。

**役割を分けて直した。** `ScanStatus` は終わっている取り込みを観測するたび、その `Scan` を
そのまま渡す（同じものを何度渡してもよい）。それが新しいかどうかは、いまの一覧がどの
取り込みまでを映しているかを知っている `LibraryPage` が id で判断する。控えにも
`scanId` を持たせるので、再生画面から戻ったときに「見ていない間に別の取り込みが終わって
いた」ことも分かる。

あわせて「**この部品が最初に見た状態**か」も渡す（`firstSight`）。最初に見た時点で既に
終わっていた取り込みは、一覧を読んだのとほぼ同時なので反映済みとみなしてよい。ここを
「初めて観測した取り込みか」で代用すると、**空のライブラリで最初の取り込みを走らせた
場合**と**開いた時点で実行中だった場合**が反映済みに倒れ、取り込んだ動画がいつまでも
出てこない（どちらも `knownScanId` が未設定のままそこへ来る）。

この形にすると、画面をまたいで生きる印を持たずに済む。一覧を開くたびの 1 ページ目の
二重取得も無くなる。判断の材料が `Scan.id` ひとつなので、実行中を一度も観測できなかった
場合（開始要求の応答だけが失われ、次の巡回までに終わっていた場合）にも気付ける。

T016 は `ScanStatus` の振る舞いを変えないと定めているが、
[contracts/screen-states.md](../../../specs/004-library-ui/contracts/screen-states.md) 4.
が求めているのは「終わったら一覧を読み直す」ことであって、開くたびに読み直すことではない。

あわせて「取り込みを始められなかった」ことを状態の取得の失敗とは別に持つようにした ──
同じ入れ物だと、押した直後の巡回が成功しただけで消え、押した利用者には始まったように
見える。文言も「取り込みを始められません: …」に分けた。ただし**消えなさすぎてもいけない**:
要求の失敗は「始まらなかった」ことを保証しないので、そのあと実行中が見えたり別の取り込みが
見えたりしたら言い分のほうが誤りである。失敗した時点で見えていた取り込みの id を添えておき、
それと違うものが見えたら引っ込める。

`web/src/components/ScanStatus.test.tsx`（観測を取りこぼさないこと）と
`web/src/pages/LibraryPage.restore.test.tsx`（新しいかどうかの判断）が固定している。

> **経緯**: ここは PR #27 のレビューで 5 回直している。最初は「実行中を見たか」という印を
> `ScanStatus` に持たせる形にし、画面をまたぐために印をモジュール変数へ移し、印を立てる
> 場所と降ろす場所をそのつど直した。印を増やすほど取りこぼす経路が増えたので、
> 最終的に印を捨てて id の比較に置き換えた。**状態を足して場合分けするより、判断に必要な
> 事実（どの取り込みまで映しているか）を持つほうが小さく収まる。**

### 「一覧へ戻る」は遷移元の URL へ帰る（T024 の付随）

`<Link to="/">` のままでは、`/?q=ねこ&sort=titleAsc` から開いた再生画面から戻ったときに
絞り込みも並び順も消え、控えの鍵（`q` と `sort` でできている）とも一致しないので復元も
効かなかった。項目のリンクに遷移元の URL を `state` で持たせ、再生画面はそれを戻り先に
する。直接開いた場合（`state` が無い）と、`/` で始まらない値は `/` に落とす。

往復そのものは `web/src/pages/LibraryPage.restore.test.tsx` が確かめている。

### 受け付ける並び順は配列ではなく `Record<VideoSort, true>` で持つ（T032）

`web/src/preferences/viewPreferences.ts` の検証表を `Record<VideoSort, true>` にした。
配列（`["addedDesc", "titleAsc"]`）だと、`api/openapi.yaml` に並び順が増えても型検査は
通ってしまい、新しい値が黙って既定値へ落とされる。`Record` なら項目が足りない時点で
落ちる。data-model.md 1. の「ここで列挙を書き写さない」を型で守る形である。

判定に `in` ではなく `Object.hasOwn` を使っているのは、`in` が原型の鎖まで見るため
`"toString"` が正しい値として通ってしまうからである（`viewPreferences.test.ts` が
この 1 件を明示的に確かめている）。

### 壊れた `?sort=` は既定値ではなく表示設定へ落とす（T037）

T015 は URL の想定外の値を「既定値に落とす」としていたが、US3 で並び順の初期値が
利用者のものになったので、落とし先を表示設定の `sort` にした。`toSort` は
`VideoSort | undefined` を返し、「URL が並び順を指していない」（無い／壊れている）
2 つの場合を呼び出し側で分けない — どちらも落とし先が同じだからである。
表示設定自体が壊れていれば `readViewPreferences` が既定値を返すので、最終的な
落とし先は変わらない。

### 密度を変えたら表示設定の `sort` は触らない（T036）

`contracts/view-preferences.md` 4. の「`sort` は現在値のまま」を、**保存されている値**
のままと読んだ。画面に出ている並び順（URL 由来）を書き戻す実装にすると、他人から
共有された `/?sort=titleAsc` を開いて密度だけ変えた利用者が、自分で選んでいない
並び順を次回の初期値として持たされる。表示設定は state に 1 つ持ち、変えた項目だけを
差し替えて書く。

### 帯を避ける高さは実測する。固定値にしない（T036、Devin Review の指摘）

密度を変えて戻した項目が sticky の帯に隠れないよう、はじめは項目に
`scroll-mt-16`（64px）を与えて `scrollIntoView` していた。これは**広い画面でしか
正しくない**。帯は `flex-wrap` で折り返すので、幅 360px では高さが 241px になり、
64px しか避けない項目は 177px ぶん帯の裏に入る（実測で再現した）。

`scrollIntoView` をやめ、帯の高さを `getBoundingClientRect` で実測して
`window.scrollTo` する形にした。`Toolbar` は帯の要素への `ref` を受け取る
（React 19 では関数コンポーネントでも `ref` がふつうの props である）。

**sticky な要素の高さを、それを避ける側が定数で持ってはならない。** 折り返し・
文字の大きさ・行数のどれが変わってもずれ、ずれたことは静的検査に出ない。

### 幅 1280px の「標準」は 6 列ではなく 5 列である（T035 の実測）

`contracts/design-tokens.md` 3. の列数の表は 1280px の「標準」を 6 列としているが、
実測は 5 列だった。表が画面幅（1280px）から左右の余白だけを引いて数えているのに対し、
一覧の器には `max-w-6xl`（1152px）が掛かっているためである。器の幅 1152px から
左右 1rem を引いた 1120px では、最小列幅 11rem + 間隔 1rem で 5 列にしかならない。

「細かい」7 列と「ゆったり」4 列は表のとおりで、ずれているのは「標準」だけである。
表は「目安。実測値は quickstart S4 で確かめる」と断っているので、**この PR では
契約を書き換えていない**。幅ごとの実測は S4（T040、Phase 6）の作業であり、そこで
表を直すか器の幅を見直すかを決める。

### `vitest.setup.ts` で `localStorage` を片付ける（T033 の付随）

表示設定は jsdom の `localStorage` に残り、同じファイル内の検査すべてで共有される。
片付けないと「密度を変えた」検査が後続の検査の初期値を書き換え、実行順で結果が
変わる。T003 は片付けを `cleanup()` だけと決めていたが、この機能が永続化する状態を
初めて持ち込んだので 1 行足した。対比の検査は node 環境で走り `localStorage` を
持たないため、有無を見てから呼ぶ。

### 列数の表は器の幅で書き直した。器の幅は変えない（T040）

T035 が持ち越した「表を直すか器の幅を見直すか」を、**表を直す**側で決めた。4 つの幅を
Chromium で実測した結果は次のとおりで、器（`max-w-6xl` = 1152px）が効き始める
1216px から先は列が増えない。

| 画面幅 | 器の幅 | 細かい | 標準 | ゆったり |
| --- | --- | --- | --- | --- |
| 360px | 328px | 2 | 2 | 2 |
| 768px | 736px | 4 | 3 | 2 |
| 1280px | 1120px | 7 | 5 | 4 |
| 2560px | 1120px | 7 | 5 | 4 |

器を外して画面幅いっぱいに広げれば表の元の値（2560px で 12〜15 列）に近づくが、
`max-w-6xl` は帯・見出し・一覧に共通で掛かっており、一覧だけ外すと帯の中の操作と
一覧の左端がずれる。**US4 は「小さな画面で破綻しない」ことを扱う（P4）**ので、広い側の
柱を組み替える変更はここでは行わず、`contracts/design-tokens.md` 3. の表を実測値に
差し替えて「器の幅で決まる」ことを明記した。契約は「表と CSS が食い違ったら CSS が
正しい」と定めており、表を実装に合わせるのはその向きに沿う。

### 帯の当たり判定は帯が与える。呼び出し側に書かせない（T039）

`--size-tap`（44px）四方の下限を `Toolbar` の子孫セレクタ
（`[&_:is(input,select,button)]:min-h/min-w`）に置いた。狙いを合わせた印（FR-003）を
すでに同じ形で与えており、**帯に操作を足した人が下限を書き忘れる経路**をどちらについても
塞ぐためである。帯の中に直接書かれていた `min-h-[var(--size-tap)]`（検索欄・並び順）は
重複するので外した。`DensitySelect`・`ScanStatus` は帯の外でも使えるので自前の下限を
残している。

子孫セレクタの詳細度は `.class :is(input,select,button)` = (0,1,1) で、要素側の実用
クラス (0,1,0) より強い。帯の中で個別に上書きしたいときは、ここを直すか
`!` 付きの実用クラスが要る。

### 検索欄は固定幅をやめる（T038）

`w-48`（192px）を外し、`flex-1 basis-48` + 親の `min-w-0` にした。`basis-48` は
「これを下回るなら折り返す」目安で、幅が足りれば帯の余りをそのまま吸う。`min-w-0` が
要るのは、入力欄の既定の最小幅が flex の縮小を止め、幅 360px で帯からはみ出すためで
ある。

### 縦長の動画は高さで頭打ちにする（T041）

`max-w-full` だけでは**縦長の動画で操作盤が画面外に出る**。実測では 360x640 の動画が
幅 1280px で 976x1735px になり、4 つの幅すべてで操作盤が最初の画面に入らなかった。
`max-h-[70dvh]` を足して、頭打ちになった分は地（`surface-sunken`）がレターボックスと
して見える形にした（`contracts/screen-states.md` 2. が「`--color-surface-sunken` の地の
上」と定めているとおりである）。

映像に `w-full` ではなく `max-w-full` を使うのは、比率を決め打たないためである
（`aspect-video` は 16:9 以外で必ず見切れるか余白が出る）。縦並びの flex なので通常は
親の幅まで伸びるが、上限を持たせておけば伸ばす側が変わってもはみ出さない。

### 動きを止める場所は 1 か所しか残っていなかった（T042）

`motion-reduce:` を要求された 4 ファイルのうち、実際に装飾的な動きを持っていたのは
`Skeleton`（明滅。T008 で最初から `motion-reduce:animate-none` 付き）と `VideoCard` の
静止画の遷移だけだった。`ScanStatus` の「進捗帯の伸び」は、T016 が帯ではなく
「済んだ数 / 総数」の 1 行を選んだ時点で存在しない。`Toolbar` も遷移を持たない。
足したのは `VideoCard` の `motion-reduce:transition-none` 1 つである。

**止めたのは遷移だけで、`opacity` の最終値は変えていない。** ホバーの手応えは残り、
狙いを合わせた印（`--color-focus`）も常に出る（Chromium で両方の設定を実測。
「受け入れ検証の結果」S8 参照）。`matchMedia` は使っていない — 判定は CSS が持つ。

### 受け入れ検証は「画面側だけ本物」にして行った（T047・T048）

`ffmpeg` も Docker も無い環境なので、実機の検証はできない。**やったふりをせずに、
測れる範囲を測って範囲を明示する**方針を採った。見本サーバー（`api/openapi.yaml` と
同じ形の応答）と Chromium でできたのは画面側の確認で、サーバー側（SQLite・`ffprobe`・
取り込み）は一切通っていない。

この区別が重要なのは SC-002 である。「最初の画面まで 240ms」は**画面の描画だけ**の
数字で、1 万行の SQLite 問い合わせの費用を含まない。一方 SC-008（1000 件読み込んだ
あとの反応）は費用のほとんどが画面側にあるので、この測り方でも意味がある
（`content-visibility` に任せた R-408 の判断がそのまま効いている）。

未実施分は [TD-009](../tech-debt.md) に残した。
