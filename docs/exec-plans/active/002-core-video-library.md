# 実行計画: 絞られたコア機能（動画ライブラリの中核）

- ステータス: 計画・設計まで完了。タスク分解と実装はこれから
- 最終更新: 2026-09-12
- 対象: [技術選定文書](../../design-docs/tech-stack-selection.md) 「8. 実装の進め方」の Phase 1（一覧と再生）に、一覧を実用にする最小限（サムネイル・題名検索・再生位置）を加えた範囲

## 目的

置いた動画が自動で一覧に並び、ブラウザで再生でき、題名で目当ての1本を探せる状態を作る。
[画面案](../../../specs/002-core-video-library/assets/ui-mockup.webp)が示す全体像のうち、
整理機能（タグ・お気に入り・コレクション）と画像の管理は含めない。

## 決定の記録

- **2026-09-12: コアの範囲を確定した。** 整理機能（タグ・お気に入り・コレクション）と
  画像（静止画）の管理は含めない。一覧・再生・検索が動いたあとの段階で扱う。
- **2026-09-12: 同一判定の鍵は「サイズ + 先頭/末尾 1MiB の SHA-256」にした。**
  技術選定文書 3.2 は BLAKE3 を挙げているが、読む量が 2MiB に固定されているため
  速度差が取り込み時間を律速しない。標準ライブラリで済ませ、依存を増やさない。
  技術選定文書の記述はこの決定に合わせて更新する（実装時のタスク）。
  詳細は [research.md R-101](../../../specs/002-core-video-library/research.md)。
- **2026-09-12: 再生位置は `content_key` を鍵に持つ。** `videos.id` に紐づけると、
  ファイルを消して置き直したときに失われる。「再構築できる索引」と「再構築できない
  利用者データ」をテーブル単位で分ける方針（技術選定文書の判断基準2）がそのまま成立する。
- **2026-09-12: 再生可否は許可リストで判定し、取り込み時に確定させる。** 未知の
  コーデックを「再生できる」と誤るより「できない」と誤る方が損失が小さい。
  一覧では列を読むだけにして、再生を試みる前に判別できる状態にする（SC-007）。
- **2026-09-12: サムネイルは JPEG にした。** WebP の方が小さいが、`libwebp` を含む
  `ffmpeg` ビルドを前提にすると実行環境の差で失敗しうる。
- **2026-09-12: 新しい依存は 2 つに絞った。** `golang.org/x/text`（NFC 正規化）と
  `react-router` v7（2画面のルーティング）。データ取得ライブラリと `sqlc` は入れない。
- **2026-09-12: 画面が増えるため、PR には画像を添える。** 本機能は
  [UI の変更を画像で示す規約](../../how-to/ui-change-screenshots.md)が初めて適用される
  変更になる。
