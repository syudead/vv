# 仕様品質レビューの手順

[仕様品質の規則](../product-specs/spec-quality.md)（Q-6）のレビューを回す手順。
対象は仕様を書く・変える作業（`docs/product-specs/` の変更、
受け入れ基準を定める作業）である。

## 前提

- reviewer は仕様作成者とは独立した人（または独立したコンテキストのセッション）とする。
  仕様作成者自身の承認は承認と数えない。
- 実装作業は承認後に始める。

## 手順

1. 仕様作成者は PR に次を揃える。Q-1 の要求原文、Q-2 の対応表、
   UI を含む場合は Q-3 の 5 観点、プレースホルダーがある場合は Q-5 の記載。
2. reviewer は Q-1〜Q-5・Q-7 に照らして判定し、結果を PR コメントに書く。
   見る観点は次のとおり。
   - 要求原文が欠けていないか（Q-1）
   - 対応先の無い基準・曖昧な対応が無いか（Q-2）
   - UI の 5 観点が抜けていないか、「存在する」だけの基準が無いか（Q-3・Q-4）
   - プレースホルダーに価値と誤認リスクの記載があるか（Q-5）
3. 不備があれば承認せず、具体的な指摘を返す。仕様作成者は直して再提出する。
4. Q-7 に当たる曖昧さ（具体化できない要求）が見つかった場合は、レビューで
   解釈を埋めない。Issue または PR コメントで質問に戻し、回答か明示的な合意が
   得られるまで承認しない。
5. 承認は PR の approve（または承認コメント）で記録する。受け入れなかった指摘が
   あれば理由を PR に残す。

## 終了条件

- reviewer の承認がある。承認なしに実装へ進まない。
- 未解決の Q-7（回答待ちの質問）がある場合は承認しない。
