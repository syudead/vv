# 技術選定: MDM（Media Data Management）

- ステータス: 採用（初版）
- 最終更新: 2026-09-12
- スコープ: 動画ファイルを管理し、ブラウザで再生できるシステムの初期実装

## 1. 前提と非スコープ

本ドキュメントは以下の前提で技術を選定する。前提が変わった場合は、
「6. 将来の拡張ポイント」に記した差し替え箇所から見直す。

| 項目 | 決定 |
| --- | --- |
| デプロイ形態 | セルフホスト（個人／自宅の1台、NAS や小型サーバー上の Docker） |
| クライアント | Web ブラウザのみ（PC／スマートフォン） |
| 動画の扱い | 既存ファイルをそのまま配信（H.264/AAC の mp4 を主対象） |
| 利用者数 | 単一ユーザー（同時視聴は1〜2セッション程度） |
| ライブラリ規模 | 〜数万本、数 TB をローカルディスク上に想定 |

非スコープ（初版では作らない）:

- 配信用トランスコード（HLS/DASH の生成）とそのためのワーカー基盤
- マルチテナント、ロールベースの権限管理、外部 IdP 連携
- CDN 配信、署名付き URL、DRM
- デスクトップ／モバイルのネイティブアプリ

## 2. 選定の判断基準

セルフホストの単一ユーザー用途であるため、スループットよりも
**運用の単純さ**と**壊れても復旧できること**を優先する。

1. **1プロセス・1コンテナで動くこと。** 常時稼働の外部ミドルウェア
   （Redis、メッセージブローカー、別 DB サーバー）を増やさない。
2. **ファイルシステムを唯一の真実とすること。** DB はインデックスであり、
   消してもスキャンで再構築できる状態を保つ。
3. **境界を機械的に守れること。** `ARCHITECTURE.md` の原則に沿い、ドメイン層が
   HTTP・DB・ffmpeg に依存しない構造を lint で強制する。
4. **段階的に重くできること。** トランスコードやマルチユーザーが必要になった
   ときに、書き直しではなく差し替えで対応できる境界を最初から引く。

## 3. 決定事項

| レイヤ | 採用 | 主な理由 |
| --- | --- | --- |
| 言語 | TypeScript（Node.js 22 LTS） | フロントと同一言語。ffmpeg は子プロセスで呼ぶため性能要件を満たす |
| HTTP サーバー | Hono（`@hono/node-server`） | 薄く、Range 配信をハンドラで完全に制御できる。API と SPA を1プロセスで配信 |
| フロント | React + Vite + TanStack Router/Query + Tailwind CSS | 静的ビルドをサーバーが配る構成が最も単純。状態管理はサーバー状態のみで足りる |
| DB | SQLite（`better-sqlite3`、WAL モード） | 単一プロセス・単一ユーザーに最適。バックアップはファイルコピー |
| スキーマ／クエリ | Drizzle ORM + 手書き SQL（検索系） | マイグレーションを型付きで管理しつつ、FTS は生 SQL で書ける |
| 全文検索 | SQLite FTS5（`tokenize='trigram'`） | 日本語をトークナイザ追加なしで部分一致検索できる。外部検索エンジン不要 |
| メディア解析 | `ffprobe` / `ffmpeg` を `spawn` で直接実行 | ラッパーライブラリ（fluent-ffmpeg）の抽象を挟まず、引数と失敗理由が明示的になる |
| 再生 | HTML5 `<video>` + プログレッシブ配信（HTTP Range / 206） | 対象が mp4 に限られるためプレイヤーライブラリ不要 |
| 字幕 | 外部 `.srt`/`.ass` をサーバーで WebVTT に変換し `<track>` で配信 | ブラウザは WebVTT のみ対応するため変換は必須 |
| 認証 | パスワード1つ（Argon2id）＋ HttpOnly Cookie セッション | 単一ユーザーに必要十分。外部公開は Tailscale / Cloudflare Tunnel 前提 |
| 非同期処理 | SQLite のジョブテーブル＋インプロセスの直列ワーカー | 再起動後に再開できる。Redis/BullMQ は運用対象を増やすため採用しない |
| ログ | pino（JSON 構造化ログ） | 単純で、後からログ収集に載せられる |
| テスト | Vitest（単体・結合）＋ Playwright（再生の E2E） | 「実際に再生が始まる」ことは E2E でしか担保できない |
| 配布 | Docker（multi-stage, debian-slim + ffmpeg）＋ Compose | `better-sqlite3` のネイティブビルドが素直に通る。musl 環境は避ける |

### 3.1 リポジトリ構成（pnpm workspaces）

```text
apps/
  server/        # Hono の HTTP 層、DI の組み立て、SPA の配信
  web/           # React SPA
packages/
  core/          # ドメインモデルとユースケース（外部 I/O への依存なし）
  db/            # SQLite スキーマ、マイグレーション、リポジトリ実装
  media/         # ffprobe/ffmpeg アダプタ、サムネイル生成、字幕変換
  scanner/       # ファイルスキャンと差分検出
```

依存方向は `apps/* → packages/{db,media,scanner} → packages/core` の一方向に
限定し、`dependency-cruiser` で CI から検証する。`packages/core` が
`better-sqlite3`・`hono`・`node:child_process` を import した時点で CI を落とす。

### 3.2 データモデルの要点

- `videos`: ファイルパス、サイズ、mtime、`content_key`、コンテナ／コーデック、
  尺、解像度、追加日時。
- `content_key`: `ファイルサイズ + 先頭1MiB と末尾1MiB の BLAKE3 ハッシュ`。
  全体ハッシュは数 TB では非現実的なため、この組み合わせで
  「リネーム・移動されただけのファイル」を同一と判定する。
- `tags` / `video_tags`: 分類。階層は持たせず、命名規約（`series:xxx`）で表現する。
- `playback_progress`: 再生位置と視聴済みフラグ。プレイヤーから数秒間隔で更新。
- `videos_fts`: `title` と `path` の FTS5 仮想テーブル（trigram）。
- `jobs`: 種別、対象 ID、状態、試行回数、最終エラー。

DB は「再構築可能なインデックス」に限定する。タグ・再生位置などの
ユーザー入力データのみが再構築不能なので、この2種類はテーブル単位で分け、
バックアップ対象と復旧手順を区別する。

### 3.3 配信パスの設計

- `GET /api/videos/:id/stream` が Range リクエストを処理し、`206 Partial Content`
  と `Accept-Ranges: bytes` を返す。シーク動作はこのエンドポイントの正しさに
  依存するため、Range の単体テスト（先頭・途中・末尾・不正範囲）を必須とする。
- Node の `createReadStream` で十分だが、回線が太い環境で CPU が問題になる場合は
  リバースプロキシへの委譲（nginx `X-Accel-Redirect` / Caddy）に差し替える。
  その判断のためにストリーミングは専用モジュールに閉じる。
- ブラウザの `<video>` は Cookie を送るため、ストリームも通常の
  セッション認証で保護できる（署名付き URL は不要）。

## 4. 採用しなかった選択肢

| 候補 | 却下理由 |
| --- | --- |
| Go（単一バイナリ配布） | 配布と性能は有利だが、フロントの TypeScript と2言語になる。今回の規模ではその認知コストに見合う利点がない |
| Python + FastAPI | ライブラリは豊富だが、フロントと言語が分かれ、依存管理とデプロイが重くなる |
| Next.js | 1つのフレームワークで完結する利点はあるが、常駐ワーカーの置き場所がなく、Range 配信もフレームワークの流儀と噛み合わない |
| SvelteKit | 軽量で有力。React を選んだのはエコシステムと将来の人手確保の観点のみで、技術的な優劣ではない |
| PostgreSQL | 単一ユーザーには過剰。別コンテナとバックアップ運用が増える。マルチユーザー化時に再検討する |
| Meilisearch / Elasticsearch | 検索品質は上だが常駐プロセスが増える。FTS5 trigram で数万件なら実用的 |
| 起動時の HLS 一括トランスコード | ストレージと CPU を大量に消費し、初版の要件（既存 mp4 の再生）に不要 |
| Redis + BullMQ | ジョブはサムネイル生成程度で、並列度も1で足りる。SQLite のジョブテーブルで代替できる |
| S3 / MinIO | ローカルディスクが真実である前提と合わず、Range 配信に中継が増える |
| Jellyfin / Plex の採用 | 既製品で要件は満たせるが、本リポジトリは自作を前提とする。機能比較の参照先としてのみ扱う |

## 5. 既知のリスクと対処

- **非対応コーデックの混入。** H.265/VP9/mkv などはブラウザで再生できない。
  取り込み時に `ffprobe` で判定し、再生不可を UI に明示する。変換は
  「6. 将来の拡張ポイント」の対象。
- **ファイル名の Unicode 正規化。** macOS 由来のファイルは NFD、Linux 上は NFC で
  扱われるため、パスは保存前に NFC へ正規化し、比較も正規化後に行う。
- **`better-sqlite3` のネイティブビルド。** Node のメジャー更新時に再ビルドが
  必要。Docker イメージのビルドを CI で回して検知する。Node 組み込みの
  `node:sqlite` が安定した段階で移行を検討する。
- **大量スキャン時の I/O 飽和。** 初回スキャンとサムネイル生成は直列実行し、
  `nice`／並列度1で回す。進捗は `jobs` テーブルから UI に出す。
- **バックアップ。** SQLite は `VACUUM INTO` でオンラインバックアップを取得する。
  動画本体はバックアップ対象外（再取得可能）とし、タグと再生位置のみを守る。

## 6. 将来の拡張ポイント

要件が増えたときに触る場所をあらかじめ決めておく。

| 将来の要件 | 差し替え箇所 |
| --- | --- |
| 非対応コーデックの再生 | `packages/media` にトランスコード実装を追加し、`stream` エンドポイントを HLS プレイリスト配信に分岐。プレイヤー側は hls.js を追加 |
| 複数ユーザー・権限管理 | 認証を OIDC に差し替え、DB を PostgreSQL へ移行（リポジトリ実装は `packages/db` に閉じている） |
| 外部公開・CDN | ストリーミングモジュールを署名付き URL 発行に差し替え、実配信をプロキシ／CDN へ委譲 |
| ジョブの並列化 | `jobs` テーブルのワーカーを複数プロセス化（`SELECT ... FOR UPDATE` 相当は SQLite の即時トランザクションで代替） |

## 7. 実装の進め方（フェーズ分け）

1. **Phase 0 — 骨組み。** monorepo、`packages/core` のドメイン型、
   dependency-cruiser による境界検証、Docker Compose、CI。
2. **Phase 1 — 一覧と再生。** スキャナ、`ffprobe` によるメタデータ取得、
   Range 配信、一覧ページ、`<video>` での再生。ここで「動画を管理して再生できる」
   を満たす。
3. **Phase 2 — 使える状態。** サムネイル（シークプレビュー用スプライト含む）、
   FTS5 検索、タグ、再生位置の保存、字幕変換。
4. **Phase 3 — 運用。** 認証、構造化ログ、バックアップ手順、E2E の整備。

実装着手時は `docs/exec-plans/active/` に実行計画を作成し、Phase 単位で
進捗と決定を記録する。
