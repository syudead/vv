# 長尺動画のシーク用スプライトを入力側シークで生成する

スプライト化で保存ファイル数は減ったが、全編のソフトウェア復号が残り、
CPUの遅いNASではシーク用生成が長時間かかる。生成側だけを変更し、
区間・最大600コマ・最大6シート・配信APIはそのまま使う。

## 生成方式の選択

50分を超えて配置の間隔が5秒より広がり、1280×720以上の画素数と10fps以上が
確認できる入力では、最大10か所を1回のFFmpegへ別々の入力として渡す。
入力前の `-ss` と accurate seek で各区間の中ほどの1秒手前まで進め、
目的の時刻まで復号してから各入力の1コマを順に連結する。HEVCのopen GOPで
目的の時刻の直後のCRA画像へ飛び、手前の画像が落ちるケースを避けるためである。各入力は独立した復号器を持ち、復号スレッド数は2にする。
次の10コマへ進む前にそのFFmpegを終了するため、入力・復号器が600個に増えることはない。

短尺はプロセスを何度も起動する費用で遅くなる。低解像度や低フレームレートも
全編復号の方が軽い場合があるため、従来の1回のFFmpegによる生成を使う。
短尺では追加のffprobeも起動しない。長尺の方式選択と抽出位置に必要な情報は
生成開始時のffprobeで取得し、解析できなければ従来方式を使う。

600回FFmpegを個別に起動する試作は、CPU時間が減ってもWindowsでの実時間が悪化した。
concat demuxerで必要区間を1回の復号器に連続して渡す試作はさらに速かったが、
HEVCの一部コマを欠落させた。このため、独立した復号器を少数ずつ使う構成にした。

## 時刻と完全性

固定フレームレートでは、従来のfpsフィルタが選ぶ区間中ほどの直前のフレームへ
入力側シークする。可変フレームレートでも、選ぶフレームが担当区間を越えないよう、
各入力を区間の終わりで切る。存在しないフレームを600回の平均フレームレート計算で
補間して作り出すことはしない。

各入力は最大1コマしか出せない。バッチの出力はフルレンジYUV420のY4Mで受け、
ヘッダ、寸法、画素形式、全フレームのバイト数とコマ数を確かめる。
不足・破損・余分なコマや途中の寸法変更があれば、バッチの結果を採用しない。
シート数だけを確かめると、欠落したコマを飛ばして後ろの場面が詰まっても検出できない。

フレームが無い区間、映像が音声より先に終わる入力、シークできない形式などでは、
バッチの一時データを片付けて全編復号へ戻す。従来のfpsとtpadによって空白と末尾を
補うため、不完全なスプライトを公開しない。切替時は理由を警告ログへ記録する。
キャンセルされた場合は全編復号を起動せず終了する。30分の上限は再試行を含む処理全体にかかる。

## 一時データと公開

バッチ間では、最初のY4Mヘッダだけを残してロスレスのフレームを1ファイルにまとめる。
実際にFFmpegが縮小・回転した後の寸法とSARを引き継ぐため、元動画の寸法から
回転や縮小結果を推定しない。最後のFFmpegがこれを従来と同じJPEG品質・格子でシート化する。

一時ファイルは呼び出し側が渡した生成用ディレクトリの子ディレクトリに置き、
成功・失敗・キャンセルのどの場合も削除する。完成済み生成物の再利用、
公開前の検査、元動画の削除や差し替え、中断したジョブの扱いは既存の
`internal/artifacts` と取り込み処理が受け持つ。生成方式だけの変更なので、
既にあるスプライトを一括で作り直す移行は追加しない。

## 検証

回帰テストでH.264・HEVC（open GOPのキーフレーム直前を含む）、回転・非正方形画素、開始時刻が0でない入力、
VFRの欠落区間、映像の早期終了、途中のバッチ失敗、キャンセルと一時データの清掃を確認する。
時刻の検査に加え、一定フレームレートの入力は従来方式と全シートをバイト単位で比較する。

速度の比較は[生成ベンチマーク](../how-to/preview-benchmark.md)の
`-kind seek` で本番の生成関数を呼ぶ。長尺HDだけでなく、短尺・低解像度も比較し、
方式選択のために既存の軽い入力が大幅に遅くならないことを確認する。
計測環境・入力条件・改善前後の時間はPRに記載する。NASのCPU、コーデック、
GOPの長さ、保存先のシーク性能によって改善幅は変わる。
