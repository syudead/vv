# 同一動画の検出と動画のシノニム（検討）

- ステータス: 検討中（未実装。採用する案は親 Issue で要求として固め、この文書は
  実装の変更の中で「採用」の形に書き直す）
- スコープ: 別々のファイルが「同じ動画」であることを見つける仕組みと、同じと決めた
  動画どうしで利用者データ（再生位置・タグ・公開フラグ）を共有する仕組み

## 今の挙動

動画の同一性は `content_key`（先頭と末尾 1MiB の SHA-256 とファイルサイズ、
`internal/scanner/content_key.go`）だけで決まる。

- バイト列が同じファイルは、置き場所がいくつあっても 1 本の動画（`videos` 1 行と
  `video_locations` 複数行）になる。移動・改名・コピーはすでに重複しない。
- 利用者データ（`playback_progress`・`video_tags`・`public_videos`）は `content_key`
  に結び付き、`videos` への外部キーを持たない（[ARCHITECTURE.md](../../ARCHITECTURE.md)
  「Rebuildable and user data」）。

この仕組みで拾えないものが 3 つある。

1. **その場での内容の変更。** 同じパスのファイルの内容が変わると
   （メタデータの書き換え、再エンコードで上書き、字幕の多重化など）、`UpsertVideo`
   （`internal/store/scan_index.go`）は所在を新しい `content_key` の動画へ付け替え、
   所在の無くなった前の動画の行を消す。前の鍵の再生位置・タグ・公開フラグは表に残るが、
   どの動画からも引かれなくなり、利用者から見ると失われる。
2. **同じ中身の別ファイル。** 再エンコード、解像度違い、コンテナの詰め替え（remux）、
   冒頭や末尾を切ったものは、バイト列が違うので別の動画になる。一覧に並ぶだけで、
   重複していることは知らされない。
3. **同じと分かっていても束ねられない。** 利用者が同じだと知っていても、タグや
   再生位置を片方に付けたら、もう片方には付かない。

タグにはシノニム（`tag_names` の `canonical = 0` の行）と統合があり、同じ意味の名前を
1 つのタグへ寄せられる（[specs/014-video-tags/data-model.md](../../specs/014-video-tags/data-model.md)
§1〜§3）。動画には、これに当たる仕組みが無い。

## 「同じ動画」の段階

| 段階 | 例 | 今 | この検討での扱い |
| --- | --- | --- | --- |
| L0 バイト一致 | コピー、移動、改名 | 1 本に束ねる | 変えない |
| L1 同じパスの後継 | タグの書き換え、同じ名前で上書き | 別の動画になり、前の利用者データが見えなくなる | 引き継ぎの候補にする（§3） |
| L2 同じ映像・同じ長さ | 再エンコード、解像度違い、remux | 別の動画 | 検出の対象（§1） |
| L3 同じ映像・一部だけ | 冒頭・末尾のカット、CM 抜き | 別の動画 | 検出は後の段階（§1.4） |
| L4 同じ作品の別の版 | 劇場版と TV 版、ディレクターズカット | 別の動画 | 自動検出はしない。利用者が手で束ねるだけ（§2） |

## 1. 検出

### 1.1 候補の絞り込み: 尺

L2 は尺がほぼ同じである。`videos.duration_ms` が ±1 秒（長い動画では ±0.5% の大きい
方）に収まる組だけを比べる。尺で並べた索引を 1 回なめれば組が出るので、本数が増えても
全組み合わせを比べない。尺が無い動画（解析の失敗・未完了）は対象にしない。

尺だけでは決めない。同じ尺の別の動画（同じ番組枠の別の回など）が珍しくないからである。

### 1.2 映像の指紋: シーク用スプライトを使う案（推奨）

取り込みはすでに、各動画のシーク用スプライト（最大 81 コマ、1 コマ最大 160 px、
間隔は `domain.NewSeekSpriteLayout` が尺から決める）を作っている
（[seek-sprite-generation.md](seek-sprite-generation.md)）。このコマから、Go の標準
ライブラリ（`image/jpeg`）と DCT の数十行で知覚ハッシュを作れる。

- 各コマを 32×32 の輝度に縮めて 2 次元 DCT をかけ、低い周波数の 8×8 成分（直流を
  除く）が中央値より大きいかどうかで 64 ビットの pHash を作る。
- 動画 1 本の指紋は、コマ順に並んだハッシュの列（最大 81 個、648 バイト）。
- 2 本の近さは、同じ番号のコマのハミング距離の中央値で測る。情報の少ないコマ
  （黒・単色・フェード。輝度の分散が小さいもの）は比較から外す。
- 尺がほぼ同じなら `NewSeekSpriteLayout` の間隔も同じになるので、コマの時刻がそろう。

利点は、ffmpeg を 1 回も余計に起動しないことである。指紋はシーク用スプライトの
公開のあとに作れる（スプライトの生成と同じ worker の後段か、別の軽いステージ）。

ハッシュを pHash にするのは、再エンコードで起きる違い（明るさ・コントラスト・ガンマの
ずれ、ぼかし、画質の劣化）に、隣り合う画素の大小だけを見る dHash より強いからである。
1 本あたり最大 81 コマを取り込みで 1 回計算するだけなので、DCT の費用は JPEG の
読み込みに比べて無視できる。クロップ・反転・ロゴに弱いのは、どちらのハッシュも同じ
である。

弱点:

- MP4/MOV のコマは区間に割り当てたキーフレームなので、GOP の違うエンコード間では
  コマの時刻が最大で GOP 長ずれる。場面の切り替わり付近のコマは一致しない。中央値で
  比べるのはこのためで、閾値は実データで決める必要がある。
- 黒帯の有無、クロップ、左右反転、焼き込み字幕、ロゴは pHash を大きく動かす。
  黒帯は縮める前に輝度の端を削れば吸収できるが、クロップと反転は扱わない。
- 以前に作った 6 シートのスプライトは今も読めるが、コマ数と間隔が今の配置と違う。
  指紋に版を持たせ、比べる 2 本の配置が違う組は比べない（スプライトを作り直すまで
  対象外）。

### 1.3 映像の指紋: 専用の抽出ステージを作る案

`ffmpeg -skip_frame nokey -vf fps=…,scale=32:32,format=gray -f rawvideo -` のように、
一定間隔の小さな灰色画像を直接パイプで受け取る。スプライトの間隔（尺依存）に縛られず、
全動画で同じ時間間隔（例: 2 秒）の列を作れるので、L3 の位置合わせにも使える。

代わりに、動画ごとにもう 1 回ファイル全体を読む。ネットワークドライブでは重い。
L3 を扱うと決めたときに足す、という順番がよい。

### 1.4 一部だけ同じもの（L3）

一定間隔の指紋（§1.3）があれば、ハッシュの列どうしのずらし量を探して、重なる区間の
長さと一致度で判定できる。本数が多いときは、コマのハッシュを帯に分けた転置索引
（LSH）で候補を引く。精度と費用の検証が要るので、最初の段階には入れない。

### 1.5 音声の指紋

Chromaprint は ffmpeg のビルドに `--enable-chromaprint` が要り、同梱の ffmpeg で
使えるとは限らない。映像を差し替えた動画（音声だけ同じ）を同じとみなす必要も
今は無いので、見送る。

### 1.6 検出の結果の置き場所

| 表 | 中身 | 区分 |
| --- | --- | --- |
| `video_fingerprints` | `content_key`、指紋の版、ハッシュ列 | 作り直せる索引（スプライトから再計算できる） |
| `video_identity_dismissals` | 「同じではない」と判断した `content_key` の組 | 作り直せない利用者データ |

候補の組そのものは保存しない。指紋と尺から毎回（または指紋ができた時点で）求める。
「同じではない」の判断だけを残し、同じ組を再び候補に出さない。

## 2. 動画のシノニム

### 2.1 考え方

タグのシノニムと同じく、「元（正）」と「別名」を持つ。

- 束ねた動画の集まりを 1 つの **同一性** とし、その正の鍵を 1 つの `content_key` に
  決める。
- 別名の `content_key` から正の鍵を引く表を足す。

```sql
-- 別名の内容の識別子から、正の識別子を引く。利用者データなので videos への外部キーは無い。
create table video_aliases (
    alias_key     text primary key,
    canonical_key text not null,
    created_at    integer not null,
    check (alias_key <> canonical_key)
) without rowid;
create index video_aliases_canonical_idx on video_aliases (canonical_key);
```

不変条件: 正の鍵は別名の行の `alias_key` に現れない（別名の別名を作らない）。どの別名も
1 回引けば正の鍵に着く。束ねる操作はこれを保つように書く。

- 束ね先が別名なら、先にその正の鍵へたどる。
- 束ね元が正の鍵なら、`canonical_key` が束ね元の行をすべて束ね先に付け替えてから、
  束ね元自身を束ね先の別名にする。たとえば `a1 → A` があるところで A を B へ束ねると、
  `a1 → B` と `A → B` になる（`a1 → A → B` を残さない）。

### 2.2 利用者データの扱い

2 つの案がある。

- **案 A（束ねるときに付け替える、推奨）。** タグの統合と同じく、束ねる操作の中で
  別名側の行を正の鍵へ移す。
  - `video_tags`: 和集合（`insert or ignore … select`）。
  - `playback_progress`: `updated_at` が新しい方を残す。
  - `public_videos`: どちらかが非公開なら非公開にする（意図しない公開を避ける）。
    どちらを採るかは要件で決める。
  - 書くときは正の鍵に書く。読むときは、利用者データを引く箇所すべてで、動画の
    `content_key` を `video_aliases` で正の鍵に置き換える（`coalesce(alias.canonical_key,
    v.content_key)` の形）。応答に載せる値だけでなく、一覧の SQL が直接引いている箇所も
    含む。
    - 視聴状態の絞り込みと再生日時の並び（`internal/store/listing.go`、
      `library_items.go` の `playback_progress` の結合）。
    - タグでの絞り込みと、検索語のタグ名への照合（`internal/store/search.go` の
      `video_tags`）。
    - ゲストに見せる所在の条件（`internal/store/visibility.go` の `public_videos`）。
    - 応答を組み立てるときの `TagsByContentKeys`・`ProgressByContentKeys`。
    どれかを置き換え忘れると、別名の動画が「正のタグが見えるのにタグで絞ると出ない」
    「公開したのにゲストに見えない」のように食い違う。
  - フォルダ由来のタグ（`video_folder_names` から付くもの）は束ねない。版ごとに置き場所の
    フォルダが違うので、各動画の `videos.id` から今までどおり求め、手で付けたタグ
    （`video_tags`、正の鍵で引く）とあとで合わせる。`TagsByContentKeys` は両方を
    同じ鍵で引いているので、手で付けたタグの側だけ正の鍵へ置き換えるよう分ける。
- **案 B（利用者データを同一性の id に結び直す）。** `playback_progress` などの鍵を
  新しい同一性 id に替える。読み書きは単純になるが、既存の 3 表の移行と、
  「利用者データは内容の識別子に結ぶ」という今の前提の書き換えが要る。

案 A は既存の表を変えず、タグの統合（[data-model.md](../../specs/014-video-tags/data-model.md)
§3）と同じ形の書き換えで済むので、こちらを推す。どちらの案でも、指紋・サムネイル・
シーク用スプライト・ホバープレビュー・ライブ変換の解析情報は `content_key` ごとのまま
である（作り直せるものは束ねない）。

### 2.3 解除

別名の行を消すと、その内容は独立した動画に戻る。利用者データは正の側に残り、戻った
動画には何も付かない（タグのシノニム解除で名前が空くだけなのと同じ）。束ねたときの
データを分けて戻すことはしない。

### 2.4 見せ方

段階を分ける。

1. **詳細画面に「他の版」。** 束ねた動画を解像度・コーデック・サイズ・置き場所と
   並べ、選んだ版で再生する。一覧は今までどおり 1 ファイル 1 件で、同一性を持つ動画に
   印を付ける。一覧の数え方・検索・フォルダのグループに影響しない。
2. **一覧で 1 件に畳む。** ライブラリの項目（`GET /api/library`）に「同一性」を
   フォルダのグループと並ぶ種類として足し、代表の版（再生できるもののうち解像度が
   最大、または利用者が選んだもの）で見せる。畳んだ項目とフォルダのグループが
   重なるとき（版が別々のフォルダにあり、それぞれがグループに属する）の規則が要る。
   検索・絞り込みは版ごとに当て、どれかが当たれば出す（グループと同じ）。

ゲストには公開フラグが同一性単位になる（案 A では正の鍵の `public_videos`）。
公開した動画の別の版も見えるようになることを、公開の操作で伝える必要がある。

### 2.5 束ねる操作

- 検出の候補一覧（管理画面）で「同じ動画」「違う動画」を選ぶ。前者は束ね、後者は
  `video_identity_dismissals` に残す。
- 一覧で複数の動画を選び、選択バーから「同じ動画として束ねる」。L4 はこの経路だけに
  なる。
- どの版を正の鍵にするかは利用者に見せなくてよい（内部の鍵である）。代表の版と
  正の鍵は別物として扱う。

## 3. 同じパスの後継（L1）

検出とは独立に、今すぐ効く改善がある。`UpsertVideo` が所在を別の `content_key` の
動画へ付け替え、前の動画の行を消すとき、前の鍵の利用者データは見えなくなる（§今の挙動）。

- 付け替えの時点で「前の鍵 → 新しい鍵」を後継の候補として記録する。
- 新しい動画の解析（probe）が終わり、尺が前の動画の尺と §1.1 の幅で一致したら、
  自動で束ねる（新しい鍵を正、前の鍵を別名にして案 A の付け替えをする）。前の尺は
  前の動画の行を消す前に候補の行へ写しておく。
- 尺が合わなければ別の動画で上書きされたものとみなし、束ねない。

これには指紋も新しい画面も要らない。一方で、同じ尺の別の動画で上書きした場合に
誤って引き継ぐ。指紋ができた段階で、後継の自動確定に指紋の一致も条件として足せる。

## 4. 進め方の提案

| 段階 | 内容 | 新しい表 | 画面 |
| --- | --- | --- | --- |
| 1 | 同じパスの後継（§3）と、`video_aliases`・案 A の読み書き | `video_aliases`、後継候補 | なし（詳細画面に束ねた版の数だけ出してもよい） |
| 2 | 手で束ねる操作と詳細画面の「他の版」（§2.4 の 1、§2.5） | なし | 選択バー、詳細画面 |
| 3 | スプライトからの指紋と L2 の候補、判断の記録（§1.2、§1.6） | `video_fingerprints`、`video_identity_dismissals` | 管理画面の候補一覧 |
| 4 | 一覧で 1 件に畳む（§2.4 の 2） | なし | ライブラリ |
| 5 | 必要なら L3（§1.3、§1.4） | 指紋の版を上げる | 候補一覧の表示の追加 |

段階 1 だけでも、今利用者データが見えなくなる経路（その場の上書き）を 1 つ塞げる。

## 未決の点

要件として親 Issue で決める必要があるもの。

- 束ねたときの公開フラグ（非公開を優先するか、公開を優先するか）と再生位置の選び方。
- 後継の自動確定を、尺の一致だけで行ってよいか。確認の画面を挟むか。
- 一覧で畳む（段階 4）ところまで要るか。「他の版」を詳細画面に出すだけで足りるか。
- L2 の判定の閾値。実際のライブラリで、同じ動画の組と、尺だけ同じ別の動画の組を
  集めて決める。
- 束ねた版の片方をディスクから消す（重複の掃除）操作まで要るか。今のシステムは
  メディアフォルダを読むだけで、ファイルを消さない。
