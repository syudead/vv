# ライブラリ UI: 見た目の規則と一覧の構成

- ステータス: 採用
- スコープ: `web/` の画面（シェル・一覧・再生）が従う見た目の規則と、その規則が
  守られていることの確かめ方

本書は「なぜこの形にしたか」だけを書く。値そのもの（色・半径・カード幅）は
`web/src/index.css` の `@theme` にあり、検査する組は
`web/src/theme/tokens.test.ts` にある。ここに写すと真実が 2 か所になるので、写さない。
**本書と実装が食い違ったら、実装が正しい。**

## 1. なぜ見た目の値を CSS の 1 か所に置き、対比をテストで保証するのか

規則の置き場は `web/src/index.css` の `@theme` だけである。画面と部品は、そこから
Tailwind が生成する実用クラス（`bg-surface`・`text-fg-muted`・`rounded-md` など）しか
使わない。生の 16 進色・`rgb()`・Tailwind 既定のパレット名（`neutral-*`・`sky-*`）を
`web/src/**` に書くことは禁止で、その禁止自体を `web/src/theme/tokens.test.ts` が
走査して落とす。

CSS を真実にしたのは、そうすると画面側にトークン名以外の選択肢が無くなるからである。
値を TypeScript 側に置いて CSS を生成する形も採れるが、画面は結局 Tailwind のクラス名で
書くので名前が二重になり、手編集禁止の管理対象が 1 つ増える。

対比を人の目に任せない。同じ `tokens.test.ts` が `@theme` から色を取り出し、
sRGB → 相対輝度 → 対比を WCAG 2 の式で計算して、文字と面の各組が 4.5 以上であることを
表明する。検証が**そのファイルを読むだけ**で済むのは、値が 1 か所に集まっている結果である。
外部の検査ツール（axe・Lighthouse）を CI に入れる案は、実ブラウザと描画が要る割に、
得られるのは対比以外の指摘であり、それは人が見る範囲である。

**文字色や面の色を足したら `tokens.test.ts` の組にも足すこと。** 組に無い色は検査されない。
テストは「組に載っているのに CSS に無い」ずれも落とすが、その逆は落としようがない。

## 2. なぜ暗い配色だけを実装し、明暗の切り替えを入れないのか

`:root` に `color-scheme: dark` を宣言し、暗い配色**だけ**を定義する。
`prefers-color-scheme` の分岐も切り替えスイッチも入れない。

理由は維持の費用である。切り替えを入れると、対比の検査対象が 2 組になる。一方は誰も
見ないまま値が古び、それでも検証対象として保ち続けることになる。

その代わり、トークン名を色そのもの（`neutral-850`）ではなく**役割**（`bg`・`surface`・
`elevated`・`fg`・`fg-muted`・`accent`・`danger`・`warning`）で付けてある。将来明るい配色が
必要になったときの作業は「もう 1 組の値を定義する」ことだけで、画面側の書き換えは発生しない。
いま分岐を持たないことと、あとで分岐を足せることは両立する。

## 3. なぜ仮想スクロールを入れないのか

一覧は仮想スクロールのライブラリを使わない。求めているのは「操作への反応がすぐ始まる」
ことであって、DOM の要素数を減らすこと自体ではない。

仮想スクロールを避けたのは、この一覧が**折り返す格子**だからである。1 行の枚数は画面幅と
カード幅で変わるので、仮想化すると枚数の計算を自前で持つことになり、一覧へ戻ったときの
位置の復元も仮想化の座標系に合わせて作り直しになる。一覧は 1 ページ 60 件ずつしか読まない
ので、DOM に載る数は利用者が読み込んだ分に限られる。依存も増えない。

**この判断は測ってから見直す。** 反応が遅いと分かった場合でも、その場で仮想スクロールへ
進まず、まず何が遅いのかを測る。

## 4. なぜ幅の分岐を CSS だけで行い、JavaScript で幅を監視しないのか

サイドバーは画面幅で展開・レール・ドロワーに変わるが、境界は Tailwind の既定の
ブレークポイントをそのまま使い、独自の境界を定義しない。`matchMedia` は読まない。

JavaScript で幅を監視すると、監視そのものに加えて、初回描画が必ず既定値で 1 フレーム出る
ちらつきと、テストのための `matchMedia` の擬似実装を抱え込む。CSS だけで済む分岐に
それを持ち込む理由が無い。

**同じ理由で、動きを減らす設定（`prefers-reduced-motion`）も CSS だけで扱う。** 装飾的な
遷移は `motion-reduce:` 変種で止め、色の最終状態と狙いの印は常に適用する ── 動きだけを
止めるので、操作の結果は判別できる。

## 5. なぜ構図の検証を機械に任せないのか

機械で確かめるのは、対比・生の色が無いこと・部品の振る舞い（選択、絞り込み、再生位置の
送信など）に限る。**構図そのものと、画面幅による出し分けは人が実機で確かめる。**

jsdom は CSS を適用しないので、`position: fixed` もメディアクエリも折り返しも解決されない。
そこに擬似的な仕掛けを置くと、「テストは通るが画面は壊れている」という最悪の状態を招く。
視覚回帰テスト（基準画像との比較）は依存が増えるうえ、環境ごとの字形差で誤検知が出るため、
以後すべての UI 変更が基準画像の更新を伴うことになる。

人に回すのは**確かめられないものだけ**である。

**未実施のまま残っている確認**: 読み上げソフトでの確認と、数千件規模の実データでの
体感は一度も行われていない。DOM が正しいことと、読まれる音・1000 件での体感が正しい
ことは別の事実である。環境が用意できたときに確かめる。

## 6. 一覧の構成

一覧は管理画面として密度の高い構成にする。構造は Stash 系の管理画面に近く、配色と書体だけ
vv 独自にしている。

- **シェル**: 上部の `TopBar` は ☰・ロゴ・取り込みの状態だけを持ち、ナビゲーションと設定は
  `Sidebar` に一本化する。同じ入口を 2 か所に置かない。
- **サイドバー**: 展開・レール（アイコンのみ）・ドロワー（狭幅）の 3 状態。折りたたんでも
  カードを拡大せず、格子が使える横幅を増やす。
- **ツールバー**: 件数・検索・絞り込み・並び順・表示倍率・更新をコンパクトにまとめる。
  狭幅では行を分け、操作そのものを縮小しない。
- **カード**: 一次情報はサムネイル・題名・再生時間・再生進捗だけとする。解像度・コンテナ・
  ファイルサイズは一覧へ出さない。カード全体を囲う重い外枠は使わない。
- **選択**: チェックは通常隠し、ポイントしたときだけ表示する。1 件でも選択されたら全件の
  チェックを表示し、画面下部に件数と「選択解除」を持つ固定バーを出す。通常のツールバーは
  選択の前後で位置や高さを変えない。hover できない端末では常時表示し、キーボードからも
  最初の選択を開始できる。
- **操作状態**: 通常・hover・focus-visible・active・selected・disabled を部品ごとにばらばらに
  せず明確に分ける。キーボードフォーカスはアクセント色の外側輪郭で示す。検索欄は内側の
  `input` ではなく外枠にフォーカスを出し、二重輪郭を避ける。

## 7. 裏側の無い入口の扱い

サイドバーには、まだ裏側の機能が無い入口（「最近追加」「視聴途中」）が並ぶ。これらは
押せる要素として描き、押すと「準備中です」と伝えるトーストを出す。

`disabled` も `aria-disabled` も付けない。どちらも「**いまは**使えない」と伝える印で、
利用者に条件を探させるためである。ここでは機能がまだ無いだけなので、押した結果として
そう言う方が短い。

**この扱いを増やさないこと。** 入口の数だけ「押しても何も起きない」場所が増える。新しい
入口は、裏側ができてから足す。

## 8. 再生画面の構成

再生画面（`/videos/:id`）は「見る」ための画面で、一覧とは逆に密度を下げる。詳細な形と
文言は [specs/012-video-detail-ia/ui-design.md](../../specs/012-video-detail-ia/ui-design.md)
にあり、ここには構成の判断だけを書く。

- **構成要素は 4 つだけ**: プレイヤー・題名・属性情報（ファイルの場所を含む）・関連動画。
  シェルも上部バーも置かず、閉じる操作は × と Esc にする。戻り先は画面を開く前の一覧で、
  関連動画や「次を再生」で移っても最初の一覧のまま引き継ぐ。
- **幅による出し分けは CSS だけ**（4 と同じ）: `lg` 以上は右に関連動画の列、それ未満は縦に
  積む。× は幅ごとに 1 つずつ DOM に置き、`hidden`／`lg:hidden` だけで見せる方を決める。
- **属性は区切り線の下の 1 列**: 英語の小さいラベルと値の組を `dl` で並べる。枠・カード・
  タブで囲わない。縦線で区切った 1 行は収まる `xl` からにし、それ未満は線の無い格子にする。
  折り返す幅で縦線を使うと、行頭に線と余白が残るからである。
- **状態と失敗はプレイヤーの中で完結させる**: 読み込み中・取り込みの段階・読み取り失敗・
  再生失敗・動画が消えた・再生終了は、プレイヤーの上の 1 つの入れ物に重ねる。同時に出すのは
  1 つだけで、入れ物が重なりの順を決める。外に出すのはプレイヤー直下の「作成中」の 1 行だけで、
  帯やトーストは使わない。層の中の文字は不透明な `bg-navbar` の面に載せ、半透明の
  `bg-overlay` の上に直接置かない（対比を `tokens.test.ts` で検査できなくなるため）。
- **video.js に入れるのは操作バーの部品だけ**: 再生速度・10 秒送り・現在時刻/長さ・
  「変換して再生中」。状態表示を video.js の部品にすると、画面の他の部分と状態を共有できない。
- **キーボード操作は画面全体で受ける**: video.js の操作バーの部品はキーの伝播を止めるので、
  `window` の捕捉段階で受け、ボタンやスライダー自身の操作になるキーだけを見送る。
- **タッチ用の中央操作は `pointer: coarse` だけ**: 出し分けはメディア条件だけで行い、
  `matchMedia` は読まない（4 と同じ理由）。
