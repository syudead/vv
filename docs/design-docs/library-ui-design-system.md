# ライブラリ UI の見た目の規則: CSS 1 か所・対比の自動検査・仮想スクロール無し

- ステータス: 採用
- 最終更新: 2026-09-16
- スコープ: `web/` の画面（一覧・再生）が従う見た目の規則の置き場と、その規則が
  守られていることの確かめ方
- 一次資料: [specs/004-library-ui/research.md](../../specs/004-library-ui/research.md)
  の R-401・R-402・R-405・R-408、および
  [specs/005-ui-refinement/research.md](../../specs/005-ui-refinement/research.md)
  の R-502・R-503・R-511（判断の経緯と検討した代替案はそちらにある）

本書は「なぜこの形にしたか」だけを書く。値そのもの（色・半径・大きさ）は
`web/src/index.css` の `@theme` にあり、検査する組は
[specs/004-library-ui/contracts/design-tokens.md](../../specs/004-library-ui/contracts/design-tokens.md)
にある。ここに写すと真実が 2 か所になるので、写さない。

1〜3 は 004（一覧 UI）で決めたもの、4〜6 は 005（原案に合わせた再構築）で足したもので
ある。

## 1. なぜ見た目の規則を CSS の 1 か所に置き、対比をテストで保証するのか

規則の置き場は `web/src/index.css` の `@theme` だけである。画面と部品は、そこから
Tailwind が生成する実用クラス（`bg-surface`・`text-muted`・`rounded-card`・
`min-h-[var(--size-tap)]` など）しか使わない。生の 16 進色・生の px・Tailwind 既定の
パレット名（`neutral-*`・`sky-*`）を `web/src/**` に書くことは禁止で、その禁止自体を
`web/src/theme/noRawColors.test.ts` が走査して落とす。

CSS を真実にしたのは、そうすると画面側にトークン名以外の選択肢が無くなるからである
（R-401）。値を TypeScript 側に置いて CSS を生成する形も採れるが、画面は結局 Tailwind の
クラス名で書くので名前が二重になり、`docs/generated/` と同じ「手編集禁止」の管理対象が
1 つ増える。

対比を人の目に任せないのは、spec の SC-006 が「100%」を求めているからである。1 か所に
値が集まっている結果として、検証は**そのファイルを読むだけ**で済む。
`web/src/theme/tokens.test.ts` が `@theme` から色を取り出し、sRGB → 相対輝度 → 対比を
WCAG の式で計算して、契約の対比表の各組が基準（文字は 4.5、境界と狙いの印は 3.0）以上で
あることを表明する（R-405）。外部の検査ツール（axe・Lighthouse）を CI に入れる案は、
実ブラウザと描画が要る割に、得られるのは対比以外の指摘であり、それは受け入れ検証で人が
見る範囲である。

**トークンを足したら契約の対比表にも足すこと。** 表に無い組は検査されない。テストは
「表に載っているのに CSS に無い」ずれも落とすが、その逆（CSS にあるのに表に無い）は
落としようがない。

## 2. なぜ暗い配色だけを実装し、明暗の切り替えを入れないのか

`:root` に `color-scheme: dark` を宣言し、暗い配色**だけ**を定義する。
`prefers-color-scheme` の分岐も切り替えスイッチも入れない（R-402）。

理由は維持の費用である。切り替えを入れると、対比の検査対象が 2 組になる。一方は誰も
見ないまま値が古び、それでも SC-006 の検証対象として保ち続けることになる。

その代わり、トークン名を色そのもの（`neutral-850`）ではなく**役割**（`surface`・
`surface-raised`・`body`・`muted`・`accent`・`danger`・`warning`・`focus`）で付けてある。
将来明るい配色が必要になったときの作業は「もう 1 組の値を定義する」ことだけで、画面側の
書き換えは発生しない。いま分岐を持たないことと、あとで分岐を足せることは両立する。

## 3. なぜ仮想スクロールを入れずに `content-visibility` に任せるのか

一覧は仮想スクロールのライブラリを使わない。各項目に `content-visibility: auto` と
`contain-intrinsic-size` を与え、画面外の項目の描画をブラウザに省かせる（R-408）。

SC-008 が求めるのは「操作への反応が 100ms 以内に始まる」ことであって、DOM の要素数を
減らすこと自体ではない。`content-visibility: auto` は画面外のレイアウトと描画を省くので、
要素数が増えても 1 フレームの費用が上がりにくい。依存も増えない。

仮想スクロールを避けたのは、この一覧が**格子**だからである。1 行の列数は画面幅と密度で
変わるので、仮想化すると列数の計算を自前で持つことになり、一覧へ戻ったときの位置の復元
（R-403）も仮想化の座標系に合わせて作り直しになる。一覧は 1 ページ 60 件ずつしか読まない
ので、DOM に載る数は利用者が読み込んだ分に限られる。

`contain-intrinsic-size` は必ず与える。省いた項目の高さを 0 と見積もらせると、スクロール
バーが暴れる。`content-visibility` に対応しないブラウザでは効果が無いだけで、表示は
壊れない。

**この判断は測ってから見直す。** 受け入れ検証（[quickstart.md](../../specs/004-library-ui/quickstart.md)
S7）で SC-008 を満たせなかった場合でも、その場で仮想スクロールへ進まず、まず
[tech-debt.md](../exec-plans/tech-debt.md) に記録する。

## 4. なぜ表示のみの要素を `disabled` でも `aria-disabled` でもなく非対話要素にするのか

原案の構図を再現するために、画面には裏側の機能が無い入口（コレクション・タグ・
お気に入り・未整理・漏斗・表示切替・設定など）が並ぶ。これらは `<button>` にも `<a>` にも
せず、`<span>` / `<li>` のまま描く。`disabled` も `aria-disabled` も付けない。読み上げ
向けには、ラベルの直後に `（未実装）` を `sr-only` で添える（[R-503](../../specs/005-ui-refinement/research.md)）。

理由は意味である。`disabled` と `aria-disabled` はどちらも「**いまは**使えない」と伝える
印で、利用者に条件を探させる。ここでは機能そのものが存在しないので、条件は永遠に揃わない。

副次的に、規則が検査しやすくなる。「押しても何も起きない」を `onClick` が無いことで
確かめると、`onClick` を足した瞬間に検査をすり抜ける。**押せる要素として存在しない**ことで
確かめれば、`web/src/layout/placeholders.test.tsx` が役割（`button` / `link`）と tab 順の
2 つを見るだけで済む。検討した代替案（`<button disabled>`・`aria-disabled` + `tabIndex={-1}`・
`aria-hidden`・そもそも描かない）とその却下理由は R-503 にある。

**表示のみの要素は `web/src/layout/` に集める。** 規約が 1 区画に閉じるので、あとで機能が
付くときに「どれが表示のみだったか」を探し回らずに済む。

## 5. なぜ幅の分岐を CSS だけで行い、JavaScript で幅を監視しないのか

サイドバーの出し入れとロゴの置き場は 640px を境に変わるが、境界は Tailwind の `sm:`
（`@media (width >= 40rem)`）をそのまま使い、独自のブレークポイントを定義しない。ロゴは
サイドバーとヘッダーの**両方に置き**、使わない側を `display: none` で消す。`matchMedia` は
読まない（[R-502](../../specs/005-ui-refinement/research.md)）。

JavaScript で幅を監視すると、監視そのものに加えて、初回描画が必ず既定値で 1 フレーム出る
ちらつきと、テストのための `matchMedia` の擬似実装を抱え込む。CSS だけで済む分岐にそれを
持ち込む理由が無い。

`display: none` で消すのが要点である。支援技術からも消えるので、DOM にロゴが 2 つあっても
製品名は 1 回しか読まれない。`visibility` や `hidden` 属性ではこうならない。`order` で
1 つを移す案や container クエリを採らなかった理由は R-502 にある。

**同じ理由で、動きを減らす設定（`prefers-reduced-motion`）も CSS だけで扱う。** 装飾的な
遷移は `motion-reduce:` 変種で止め、色の最終状態と狙いの印（`--color-focus` の輪郭）は
常に適用する ── 動きだけを止めるので、操作の結果は判別できる。

## 6. なぜ構図の検証を機械に任せないのか

機械で確かめるのは、対比と明暗の順序・表示のみの要素が対話要素でないこと・密度の読み替えの
往復・情報パネルの体裁の 4 つに限る。**構図そのものと、画面幅による出し分けは人が原案と
並べて確かめる**（[R-511](../../specs/005-ui-refinement/research.md)）。

jsdom は CSS を適用しないので、`position: fixed` もメディアクエリも
`grid-template-columns` も解決されない。そこに擬似的な仕掛けを置くと、「テストは通るが
画面は壊れている」という最悪の状態を招く。視覚回帰テスト（基準画像との比較）は依存が
増えるうえ、環境ごとの字形差で誤検知が出るため、以後すべての UI 変更が基準画像の更新を
伴うことになる。

人に回すのは**確かめられないものだけ**である。DOM と CSS のテキストだけで確かめられる
事柄は機械が見る ── 上の 4 つがそれで、人の目は構図と画面幅に集中する。手順は
[specs/005-ui-refinement/quickstart.md](../../specs/005-ui-refinement/quickstart.md) の
S2〜S7 にあり、そこで撮った画像を PR に添える（[ui-change-screenshots.md](../how-to/ui-change-screenshots.md)）。
