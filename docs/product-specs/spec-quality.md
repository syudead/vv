# 仕様品質の規則: 要求の縮退を防ぐ

仕様を書く・変えるときに従う規則。Issue #43
「ユーザーの意図が弱い仕様へ縮退することを防ぐ」の完了条件を文書化したもの。

狙いは1つである。**曖昧だが本質的なユーザー要求を、機械的に検査しやすい離散条件だけへ
変換しない。** 忠実に実装してもユーザーが求める成果物にならない仕様を、仕様の段階で落とす。

## 規則

### Q-1: 元のユーザー要求を引用または明示的に保持する

spec は元のユーザー要求を要約せず、引用または明示的な保持として含める。
要約は解釈であり、解釈の時点で縮退が始まる。要求が口頭・チャット等の非定型で与えられた
場合は、日時と発言者を添えて書き写す。

### Q-2: 各 Success Criterion がどの要求を満たすか追跡できるようにする

Success Criterion ごとに、Q-1 のどの要求（のどの部分）を満たすのかを対応付ける。
対応先の無い基準は書かない。対応先が曖昧な基準は、要求が曖昧なまま仕様化されている
証拠なので、Q-7 に従って明確化へ戻す。

### Q-3: UI 仕様には 5 観点の基準を書く

UI を含む仕様では、部品の有無だけでなく次の5観点の基準を明文化する。

- 視覚的階層（何が主で何が従か）
- 情報密度（詰めるのか空けるのか）
- 余白のリズム
- タイポグラフィ
- 操作の優先順位（何を先に触れるべきか）

あわせて次も書く。誰が何を改善されたと感じるべきか、現状のどこが「まともでない」のか、
参照画像から維持すべき視覚的特徴は何か、何を変えると要求を満たしたことにならないか。

### Q-4: 「要素が存在する」だけでは UI 品質の基準を満たせない

部品の有無と並び順だけを判定する Success Criterion は、UI 品質の基準として認めない。
基準には、Q-3 の観点で「どうあれば良いのか」が判定できる形で書く。
数値化できない総合評価（「実用品に見えるか」等）は数値に無理やり落とさず、
人がどの観点で判定するかを書く（非目標: すべてを数値だけで定義しない）。

### Q-5: プレースホルダーを追加する場合は価値と誤認リスクを明示する

操作不能な要素・裏側の無い入口を置く場合は、1 件ごとに次を書く。

- 置くことで得られるユーザー価値
- 利用者が「使える」と誤認するリスクと、その抑止策

価値に対して誤認リスクが見合わないものは置かない。「構図を埋める」は価値ではない。

### Q-6: 仕様作成者とは独立した reviewer が承認するまで実装へ進まない

仕様を書く・変える作業は、仕様作成者とは独立した reviewer の承認を
[レビュー手順](../how-to/spec-quality-review.md)で受ける。承認が無いまま
実装作業へ進まない。
reviewer は実装上の都合の説明ではなく、Q-1〜Q-5 と Q-7 に照らして判定する。

### Q-7: 具体化できない曖昧さは独自解釈せず、明確化へ戻す

曖昧な要求を十分に具体化できない場合は、もっともらしい解釈で埋めない。
Issue や PR のコメントで質問に戻し、回答または「この曖昧さのまま進める」という
明示的な合意が得られるまで仕様を固めない。合意なき解釈は縮退の入口である。

## 非目標

- すべての UI を数値だけで定義すること
- デザイナー不在時にモデルの判断を禁止すること
- 原案への完全なピクセル一致を要求すること
